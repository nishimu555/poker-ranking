## 2. 目的

コンポーネント設計書（`docs/b1_design/component-design.md`）と設計判断の記録（`docs/b1_design/decisions/`）をもとに、開発の前提（ディレクトリ構成、ツール、テスト、デプロイ等）を定め、Component をタスク（`Task-XXX`）に分解する。タスクごとに依存関係・完了条件・テスト期待値の概要を定め、c2（実装）と c3（テスト計画）の根拠とする。

#### 開発の前提

- [x] **Question-001**：ディレクトリ構成とビルドの有無を選んでください。
  - 根拠：Decision-0007 により GAS のプロジェクトは集計用と閲覧用の 2 つになる。CLAUDE.md 4. により Small テストはローカルで実行する必要があるが、GAS のコードは全ファイルが同じ場所（グローバル）で動き、画面の JavaScript は HTML ファイルの中に書く必要がある。ローカルのテストから関数を読み込む方法と、GAS に送るファイルの作り方の記載がない。
  - 選択肢：
    - (a) `src/aggregate/`（集計用）、`src/viewer/`（閲覧用。サーバー側と画面）に分け、GAS に送るファイルはビルド用のスクリプトで `dist/aggregate/`、`dist/viewer/` に生成する（画面の JavaScript は `.js` で書き、ビルド時に HTML に埋め込む）。テストは `tests/` に置く
      - 良い点：画面の関数（無害化、画像に描く内容の計算等）も `.js` のままローカルでテストできる（component-design.md 7. テストのしやすさ）
      - 悪い点：ビルド用のスクリプトが必要になる
    - (b) `src/aggregate/`、`src/viewer/` に GAS に送る形のファイルをそのまま置く（ビルドなし）。画面の JavaScript は HTML ファイルの中に書く
      - 良い点：ビルドが不要で、GAS のエディタ上のファイルと手元のファイルが一致する
      - 悪い点：HTML の中の関数をローカルでテストできず、画面の関数の Small テストが書けない
  - 推奨：(a)。CLAUDE.md 4.（Small テストはローカルで実行する）と、component-design.md 7.（画面の表示用の整形・画像に描く内容の計算を Small テストで確認する）を満たすため。
  - 開発者回答：(a)

  - AI確認結果：(a) `src/aggregate/`・`src/viewer/` に分け、ビルド用のスクリプトで `dist/aggregate/`・`dist/viewer/` に GAS に送るファイルを生成する方式（画面の JavaScript は `.js` で書き、ビルド時に HTML に埋め込む。テストは `tests/`）で確認した。Decision-0003（外部ライブラリなし）、Decision-0007（2 プロジェクト）、CLAUDE.md 4.（Small テストはローカル）と矛盾しない。本 plan「6. 成果物の構成予定」に反映した。（2026-09-26 22:31）
