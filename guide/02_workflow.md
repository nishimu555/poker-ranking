# 使い方

## 1. 基本のサイクル

どの工程も、同じコマンドを繰り返し実行します。AI が plan ファイルの状態を見て、次に何をするかを判断します。

| 順番 | 開発者の操作 | AI の動作 |
|---|---|---|
| 1 | `/工程のコマンド` を実行 | plan ファイル（`plans/<工程>.md`）を作り、質問（☐）を書いて止まる |
| 2 | plan ファイルの質問に回答を書く。追加の質問・指示があれば dev 項目を書く | ― |
| 3 | `/z9-answer-review <工程記号>` を実行 | 回答を確認し、問題なければ ☑ を付ける。不足があれば追加の質問を書く |
| 4 | 2〜3 を、すべて ☑ になるまで繰り返す | ― |
| 5 | `/工程のコマンド` を実行 | 成果物を作り、「レビュー待ち」にして止まる |
| 6 | 成果物をレビューする | ― |
| 7a | 指摘がある場合：plan の「9. レビュー指摘」に review 項目を書き、`/工程のコマンド` を実行 | 成果物を修正し、再レビューを依頼する（6 に戻る） |
| 7b | 指摘がない場合：plan の「1. 進捗」の「6. 成果物レビュー」に ☑ を付け、`/工程のコマンド` を実行 | 工程を「完了」にし、次の工程を案内する |

全工程の状況は `plans/README.md` で確認できます。

## 2. plan ファイルへの書き方

plan ファイルは、AI と開発者のやり取りの場です。開発者が書くのは次の 3 か所です。

### AI からの質問に回答する（Question）

「開発者回答：」の後ろに回答を書きます。それ以外の行は変更しません。

```markdown
- [ ] **Question-001**：ランキングの集計期間は？
  - 根拠：request.md の Request-3-1 に期間の記載がない
  - 選択肢：(a) 月ごと (b) 通算 (c) 両方
  - 推奨：(c)。Request-1-1 に「月間の成績と通算の成績を見たい」とあるため
  - 開発者回答：(c) でお願いします。月は毎月 1 日始まり。   ← ここを書く

  - AI確認結果：
```

☑ は AI が付けます。開発者は付けません。

### 開発者から質問・指示を出す（dev）

「8. 質問・指示」の「開発者からの質問・指示」に追記します。ID（`dev-001`）は省略しても AI が付けます。

```markdown
- [ ] **dev-001**：ランキングは上位 10 名だけ表示してほしい
  - AI対応内容：

  - AI確認結果：
```

追記後に `/z9-answer-review <工程記号>` を実行します。

### 成果物のレビュー指摘を書く（review）

「9. レビュー指摘」に追記します。ID（`review-001`）は省略しても AI が付けます。

```markdown
- [ ] **review-001**：Feature-004 の受け入れ条件に、同点の場合の扱いが書かれていない
  - AI対応内容：

  - AI確認結果：
```

追記後に `/工程のコマンド` を実行します（z9 ではありません）。

## 3. 工程ごとの注意

### a1 要件定義

- `docs/a0_request/request.md` のステータスが「確定」でないと始まりません。
- 確定後に依頼書を変更した場合は、a1 の plan に dev 項目で変更内容を伝えます。

### b1 コンポーネント設計

- 技術（言語、フレームワーク、データベース等）は、AI が選択肢と推奨を示し、開発者が回答で決めます。決定は `docs/b1_design/decisions/` に記録されます。
- 画面がある場合は、HTML のモックで確認します。
  1. 最初の plan で、見た目の基準と、画面ごとの案の数を質問されます。
  2. 回答して `/z9-answer-review b1` の後、`/b1-design` を実行すると、`plans/b1_mockups/` にモックが作られます。
  3. `plans/b1_mockups/index.html` をブラウザで開いて確認します。
  4. 採用する案を回答し、修正点は dev 項目に書いて `/z9-answer-review b1` を実行します。「別の案も見たい」場合は、案の数も書いてください（書かないと数を質問されます）。

### c1 実装計画

- 開発の前提（ディレクトリ構成、コーディング規約、静的解析、脆弱性チェックと許容する基準、テストの実行環境、デプロイの方法、ブランチ運用）を質問されます。
- タスクごとに「テスト期待値の概要」が書かれます。c2 のテストはこれをもとに作られるので、レビューでよく確認してください。

### c2 実装

| コマンド | 動作 |
|---|---|
| `/c2-implement` | 次のタスクを 1 つ実装して止まる |
| `/c2-implement 連続` | 止まる理由がない限り、残りのタスクを続けて実装する |

- AI はタスクごとに、テストを先に書き、失敗を確認してから実装します。
- **コミットは開発者が行います。** AI が報告するコミットメッセージの案（`[Task-001] 概要`）を使ってコミットしてください。
- 前のタスクがコミットされていないと、先に進めてよいか確認されます。
- 実装したファイルの一覧は `docs/c2_implement/implementation-design.md`（実装設計書）で確認できます。

### c3 テスト計画

- c2 と並行して進められます。
- 合格の基準（全件成功が必要か等）を質問されます。
- テストケースごとに、実行環境（ローカル／デプロイ先／実機）と実行者（AI／開発者）が決まります。

### c4 テスト

1. `/c4-test` を実行すると、AI が実行できるテストを実行し、開発者が実行するテストを準備して止まります。
2. 開発者は `docs/c3_test-plan/test-plan.md` の「6. 開発者が実行するテストの手順」に従ってデプロイ・テストし、結果を `docs/c4_test/test-report.md` の結果欄に書きます（成功／失敗、実施日、失敗時の状況）。
3. `/c4-test` を実行すると、AI が集計・判定します。
4. 不合格の場合は「c2 に戻して修正する」か「失敗を許容する」かを質問されます。
5. 修正後の再テストでは、AI のテストは全件、開発者のテストは変更の影響を受けるものだけが対象になります。全件やり直したい場合は dev 項目で指示します。

### d1 セットアップ手順

- 手順書の対象読者と範囲を質問されます。
- AI は一時フォルダで手順を試します。デプロイ等の手順は開発者が試し、結果を `docs/d1_setup/setup-guide.md` の「8. 検証の記録」に書きます。

## 4. 差し戻し

後の工程で前の工程の不備が見つかった場合、AI は前の工程の plan に質問を追記し、その工程を「差し戻し」にします。

1. `plans/README.md` で、差し戻された工程を確認します。
2. その工程の plan の質問に回答し、`/z9-answer-review <工程記号>` を実行します。
3. その工程のコマンドを実行して成果物を更新し、レビューします。
4. 差し戻しが解消するまで、後の工程は進みません。

## 5. ステータスの見方

| ステータス | 意味 | 開発者がすること |
|---|---|---|
| 未着手 | plan がまだない | 工程のコマンドを実行する |
| 回答待ち | 質問・指示に ☐ がある | 回答を書き、`/z9-answer-review` を実行する |
| 確定 | 質問がすべて ☑ | 工程のコマンドを実行する |
| レビュー待ち | 成果物ができた | レビューする |
| 完了 | レビュー済み | 次の工程に進む |
| 差し戻し | 他の工程から質問が追加された | 回答を書き、`/z9-answer-review` を実行する |
