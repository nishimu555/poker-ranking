# テスト（c4-test）

本スキルは `CLAUDE.md` のルールに従う。

## 役割

テスト計画どおりに実行し、結果を事実のまま記録するテストエンジニアとして作業する。

- 担うこと：Medium・Large のテストを作成し、実行者が AI のテストを実行する。開発者が実行するテストの準備を行い、すべての結果を集計して合格の基準で判定する。失敗の切り分けを客観的な基準で行う。
- 決めないこと：失敗を許容するかどうか、コードの修正方針。開発者が決める。`src/` は修正しない（修正は c2 で行う）。

## 入力と成果物

| 項目 | パス |
|---|---|
| 入力 | `docs/c3_test-plan/test-plan.md`、`docs/c2_implement/implementation-design.md`、`docs/b1_design/component-design.md`、`src/`、`tests/` |
| plan ファイル | `plans/c4_test.md`（テンプレート：`templates/plan.md`） |
| 成果物 | `tests/`（Medium・Large テスト、Small テストへの `Test-XXX` の追記） |
| 成果物 | `docs/c4_test/test-report.md`（テンプレート：`templates/c4_test-report.md`） |

参考にする開発手法：Google テストサイズ分類（サイズ別の結果集計）

## 1. 開始条件の確認

1. `plans/c2_implement.md` と `plans/c3_test-plan.md` のステータスがいずれも「完了」であることを確認する。満たさない場合は処理を行わず、その旨を報告して停止する。
2. 入力を読み込む。`src/`・`tests/` は `implementation-design.md` を読んだうえで、必要なファイルのみを読む。
3. `plans/c4_test.md` と `docs/c4_test/test-report.md` の状態を確認し、次のいずれかの処理を行う。

| 状態 | 処理 |
|---|---|
| plan ファイルが存在しない | 「3. plan の作成」 |
| 「8. 質問・指示」に ☐ が残っている | 「4. 未完了項目の提示」 |
| 「8. 質問・指示」がすべて ☑、かつテスト報告書が存在しない、または最新の実施回の後に c2 の修正（コミット）がある、または再テストの指示が ☑ になっている | 「5. テストの実施（実施回の開始）」 |
| 最新の実施回に、実行者が開発者のテストで結果が空欄のものがある | 「6. 開発者のテスト結果待ち」 |
| 最新の実施回のすべての結果が記載済みで、判定が未実施 | 「7. 集計と判定」 |
| 「レビュー待ち」かつ「9. レビュー指摘」に ☐ が残っている | 「8. レビュー指摘への対応」 |
| 「レビュー待ち」かつ「1. 進捗」の「6. 成果物レビュー」が ☑、「9. レビュー指摘」がすべて ☑ | 「9. 完了処理」 |
| 「レビュー待ち」かつ上記以外 | 開発者のレビュー待ちである旨を報告して停止する |

## 2. 作業手順の定義

plan の「5. 作業手順と実行結果」には、次の手順を記載する。本工程は実行を伴うため、各手順に「実行結果」を記載する。実施回を重ねる場合は、実施回ごとに 5-2〜5-7 の手順を追記する（例：「5-4（第2回）」）。

| 手順 | 作業内容 | 参照元 | 作成・更新先 |
|---|---|---|---|
| 5-1. 実装設計書とコードの照合 | `implementation-design.md` のディレクトリ構成・ファイル一覧・テストファイル一覧が、`src/`・`tests/` と一致していることを確認する | `implementation-design.md`、`src/`、`tests/` | `test-report.md`（6. 実装設計書との照合結果） |
| 5-2. Small テストへの ID の追記 | Small テストに `// Test-XXX（Task-XXX 期待値N）` を追記する。テストの内容は変更しない | `test-plan.md`（4. Small テストケース） | `tests/` |
| 5-3. Medium・Large テストの作成 | 実行者が AI の Medium・Large テストを、テスト計画の手順・期待される結果に従って作成する | `test-plan.md`（5. Medium・Large テストケース） | `tests/` |
| 5-4. AI のテストの実行 | 実行者が AI のテストをすべて実行する | `tests/` | `test-report.md`（4. 実施記録） |
| 5-5. 開発者のテストの準備 | 実行者が開発者のテストについて、テスト用のコード・デプロイ用スクリプトが揃っていることを確認し、再テストの対象を選ぶ | `test-plan.md`（6. 開発者が実行するテストの手順） | `test-report.md`（4. 実施記録、5. 開発者が実行するテスト） |
| 5-6. 開発者の結果の確認と集計 | 開発者が記載した結果を確認し、最新の結果を集計する | `test-report.md`（4. 実施記録） | `test-report.md`（2. 集計） |
| 5-7. 合格の基準による判定 | テスト計画の合格の基準に従って判定する | `test-plan.md`（7. 合格の基準） | `test-report.md`（3. 判定） |

## 3. plan の作成

1. `templates/plan.md` に従って `plans/c4_test.md` を作成し、「5. 作業手順と実行結果」に「2. 作業手順の定義」の手順を記載する。
2. 次の確認観点ごとに根拠資料の記載有無を確認し、記載がない・曖昧・矛盾する観点は Question 項目として記載する。

| # | 確認観点 | 確認内容 |
|---|---|---|
| 1 | テストケースの明確さ | 各テストケースの手順・期待される結果が、テストを作成・実行できる程度に明確か |
| 2 | 実行環境 | 実行者が AI のテストの実行環境・ツールが、この環境で利用できるか（バージョン確認コマンド等で確認し、結果を事実として記載する） |

3. テスト計画そのものに不足・矛盾がある場合は c3 の plan に Question 項目を追記し、「10. 他工程への影響」に従って差し戻す。
4. 「6. 成果物の構成予定」に、テストケースの件数（サイズ別、実行者別）を記載する。
5. 「1. 進捗」の「1. plan 作成」に ☑ と日時を付ける。Question 項目がある場合はステータスを「回答待ち」とする。Question 項目がない場合は「8. 質問・指示」がすべて ☑ の状態として扱う。
6. テストの作成・実行は行わない。

## 4. 未完了項目の提示

1. 「8. 質問・指示」の ☐ の項目を一覧で提示する。
2. 開発者の回答・指示の記載後に `/z9-answer-review c4` を実行するよう案内して停止する。
3. plan・成果物は変更しない。

## 5. テストの実施（実施回の開始）

1. ステータスが「確定」でない場合は「確定」とし、「1. 進捗」の「4. plan 確定」に ☑ と日時を付ける。
2. `templates/c4_test-report.md` に従って `docs/c4_test/test-report.md` を作成する（存在しない場合）。テスト報告書の「4. 実施記録」に新しい実施回（第N回）を追記する。前の実施回の記録は変更しない。
3. 第1回は手順 5-1〜5-5、第2回以降は手順 5-1、5-4、5-5（テストの変更が必要な場合は 5-2、5-3 も）を実行し、それぞれ ☑ と実行結果を記載する。
4. 実施回に次を記載する。
   - 前の実施回からの変更（第2回以降）：変更したファイル、修正のきっかけ（`c2/Question-XXX` 等）
   - 再テストの対象と選定の根拠（下記「再テストの対象の選び方」）
   - 結果の表：実行者が AI のテストは AI が結果を記載する。実行者が開発者のテストは、再テストの対象であれば結果欄を空欄とし、対象外であれば「引継ぎ（第N回：<結果>）」と記載する。
5. 実装設計書とコードが一致しない場合は、c2 の plan に Question 項目を追記して差し戻す。
6. 実行者が開発者のテストで結果欄が空欄のものがあれば「6. 開発者のテスト結果待ち」、なければ「7. 集計と判定」に進む。

### 再テストの対象の選び方

- 実行者が AI のテストは、毎回すべて実行する。
- 実行者が開発者のテストは、第1回はすべてを対象とする。第2回以降は、次の手順で機械的に選ぶ。
  1. 前の実施回から今回までの変更ファイルを `git diff` で特定する（修正コミットの `[Task-XXX]` も参照する）。
  2. 変更ファイルから、`implementation-design.md` のファイル一覧により影響を受ける Component を特定する。
  3. `component-design.md` の依存関係により、その Component に依存する Component も含める。
  4. 上記の Component を対象とする、実行者が開発者のテストを `test-plan.md` から選ぶ。
- 開発者が dev 項目で追加の再テスト・全件の再テストを指示した場合は、それに従う。

### テストが失敗した場合の切り分け

- テストのコードがテスト計画（条件・手順・期待される結果）と一致しない場合：テストのコードを修正して再実行し、修正内容を実行結果に記載する。
- テストのコードがテスト計画どおりの場合：実装の不具合として結果を記録する。`src/` は修正しない。
- 原因を推測で記載しない。記載するのは、期待される結果と実際の結果の差異などの事実のみとする。

## 6. 開発者のテスト結果待ち

1. 最新の実施回で結果欄が空欄の、実行者が開発者のテストを一覧で提示する。
2. `docs/c3_test-plan/test-plan.md`「6. 開発者が実行するテストの手順」に従ってデプロイ・実施し、結果を `docs/c4_test/test-report.md` の該当欄に記載したうえで `/c4-test` を実行するよう案内して停止する。
3. 開発者の結果欄は変更しない。空欄のテストは「未実施」として扱い、合格としない。

## 7. 集計と判定

1. 手順 5-6：開発者が記載した結果が「成功／失敗」と実施日の形式で記載されていることを確認する。形式が不明確な場合は Question 項目で確認する。テストごとに最新の実施回の結果を「2. 集計」にサイズ別・実行者別で集計する。
2. 手順 5-7：テスト計画「7. 合格の基準」に従って判定し、「3. 判定」に記載する。
3. 合格の基準を満たす場合：「1. 進捗」の「5. 成果物作成」に ☑ と日時を付け、ステータスを「レビュー待ち」とする。既存の成果物を更新した場合で「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。
4. 合格の基準を満たさない場合：判定結果と失敗したテストの一覧（事実のみ）を示し、次の選択肢を記載した Question 項目を追記して、ステータスを「回答待ち」とし停止する。
   - c2 に差し戻して修正する（修正後、次の実施回で再テストする）
   - 失敗を許容して先に進める（許容した失敗と理由を「3. 判定」に記載する）
5. 開発者の回答が「c2 に差し戻す」の場合は、c2 の plan に Question 項目を追記して差し戻す（「10. 他工程への影響」）。c2 の修正・完了後に `/c4-test` を実行すると、新しい実施回を開始する。

## 8. レビュー指摘への対応

1. 「9. レビュー指摘」の ☐ の review 項目それぞれについて、指摘に基づきテストのコード・テスト報告書を修正する。
   - ID がない場合は、開発者の記載内容を変更せず ID のみを付与する。
   - テストのコードを修正した場合は、新しい実施回で再実行する。
   - 修正箇所を「AI対応内容」に記載し、☑ を付け、「AI確認結果」に確認内容を記載する。
2. 指摘が実装の修正を伴う場合は c2、テスト計画の変更を伴う場合は c3 の plan に Question 項目を追記して差し戻す。
3. 指摘の解釈が一意に定まらない場合、または根拠資料・確定事項と矛盾する場合は ☑ を付けず、「8. 質問・指示」に Question 項目を追記し、ステータスを「回答待ち」として停止する。このとき「1. 進捗」の「2.」〜「5.」の ☑ を外す。
4. 成果物を修正した場合、「1. 進捗」の「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。
5. 修正後もステータスは「レビュー待ち」のままとし、開発者に再レビューを依頼する。

## 9. 完了処理

1. ステータスを「完了」とする。
2. 次工程（`/d1-setup`）の実行を案内する。

## 10. 他工程への影響

- 実装の不具合、実装設計書とコードの不一致は c2、テスト計画の不足・矛盾は c3 の plan ファイルに Question 項目を追記して差し戻す。
- 成果物を更新した場合、後続工程（d1）の plan ファイルが存在していれば、影響先の plan ファイルに Question 項目を追記して差し戻す。
- いずれも `CLAUDE.md`「6. 工程ゲート」に従う。影響先の plan の本文・成果物は変更しない。影響先の plan のステータスを「差し戻し」とし、「1. 進捗」の「2.」〜「5.」の ☑ を外す。「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。

## 11. 記録

1. plan ファイル・テスト報告書の「変更履歴」に、変更内容と根拠を追記する。
2. `plans/README.md` の c4 のステータスと未完了項目数を更新する。

## 12. 報告

チャットで次を報告して停止する。

1. 実施した処理（plan の作成／未完了項目の提示／テストの実施／開発者のテスト結果待ち／集計と判定／レビュー指摘への対応／完了処理）
2. 作成・更新したファイル
3. 実施回と、テスト結果の件数（サイズ別、実行者別：成功／失敗／未実施）
4. 失敗したテストの一覧（事実のみ）
5. 追加した Question 項目の一覧（ある場合）
6. 差し戻した工程（ある場合）
7. 次に行うこと
   - 開発者のテストが未実施の場合：実施するテストの一覧、手順の場所（`test-plan.md`「6.」）、結果の記載先（`test-report.md`）、記載後に `/c4-test` を実行すること
   - 「8. 質問・指示」に ☐ が残っている場合：回答・指示の記載後に `/z9-answer-review c4` を実行する
   - 「レビュー待ち」の場合：`docs/c4_test/test-report.md` と `tests/` をレビューし、指摘があれば plan の「9. レビュー指摘」に追記、指摘がなければ「1. 進捗」の「6. 成果物レビュー」に ☑ を付けて `/c4-test` を実行する
   - 「完了」の場合：`/d1-setup` を実行する
