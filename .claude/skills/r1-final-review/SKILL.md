# 実装の最終レビュー（r1-final-review）

対象工程：`$ARGUMENTS`

本スキルは `CLAUDE.md` のルールに従う。本スキルは点検と記録のみを行い、成果物（`src/`、`tests/`、`docs/`）を修正しない。指摘への対応は、開発者の判断を受けて対象工程のスキル（`/c2-implement`、`/c4-test`）が行う。

## 役割

Microsoft SDL に準拠するセキュリティレビューアとして、実装が計画・設計に忠実で、意図しない振る舞いや脆弱性を含まないかを点検する。

- 担うこと：成果物を読み取りのみで点検し、問題を事実（場所、起こりうること、起こる条件）と推奨（直し方と根拠）に分けて記録する。点検できなかった観点を理由とともに明らかにする。
- 決めないこと：指摘に対応するかどうか、直し方。開発者が決める。

参考にする開発手法：Microsoft SDL（静的解析、脅威分析：STRIDE、依存ライブラリの確認）、Microsoft Engineering Playbook（コードレビュー）

## 1. 対象の特定と開始条件

1. 工程記号が `c2` または `c4` でない場合は、処理を行わず、工程記号の指定を求めて停止する。
2. 対象の plan ファイル（`plans/c2_implement.md` または `plans/c4_test.md`）のステータスが「レビュー待ち」であり、「1. 進捗」の「6. 成果物レビュー」が ☐ であることを確認する。満たさない場合は処理を行わず、その旨を報告して停止する。
3. 「9. レビュー指摘」に、「開発者判断」が空欄の ☐ の ai-review 項目が残っている場合は、点検を行わず、その一覧を提示して停止する（同じ指摘の重複を避けるため）。
4. 判断の根拠として、`CLAUDE.md`「2. 基本原則」に記載された資料のうち、次を読み込む。
   - `docs/c1_implementation-plan/implementation-plan.md`（2. 開発の前提、4. タスクの詳細のテスト期待値）
   - `docs/b1_design/component-design.md`（7. 横断的な関心事）、`docs/b1_design/decisions/`
   - 対象工程の plan ファイル、`docs/c2_implement/implementation-design.md`（c4 の場合は加えて `docs/c3_test-plan/test-plan.md`、`docs/c4_test/test-report.md`）
5. `src/`・`tests/` は `implementation-design.md` を読んだうえで、点検に必要なファイルを読む。

## 2. 点検の範囲と守ること

### 点検の範囲

| 工程 | 対象のファイル | 対象のコミット |
|---|---|---|
| c2 | `src/`、`tests/`、`scripts/`、`deploy/`、設定ファイル（`package.json`、`eslint.config.js`、`jest.config.js`、`.gitignore`、`.devcontainer/` 等）、`docs/c2_implement/`、`plans/c2_implement.md` | c2 の plan の「コミット」欄に記録された最初のコミットから `HEAD` まで |
| c4 | `tests/`、`docs/c4_test/`、`plans/c4_test.md`、c4 で追加・変更した設定・スクリプト | c4 の作業のコミット（plan・テスト報告書の記録で特定する。特定できない場合は開発者に範囲を確認して停止する） |

### 守ること

- 読み取りのみとする。編集してよいのは、対象工程の plan ファイルの「9. レビュー指摘」「10. 変更履歴」と `plans/README.md` のみとする。
- git は確認のコマンド（`git status`（`--ignored` を含む）、`git log`、`git show`、`git diff`、`git ls-files`、`git check-ignore`）のみを実行する。
- `dist/` の中身を確認するための `npm run build` は実行してよい（`dist/` は Git の管理対象外で、ビルドのたびに作り直される）。
- 外部との通信を伴うコマンドは `npm audit` のみとする。デプロイ（`clasp push` 等）、依存ライブラリの導入は行わない。
- 点検用の一時的なスクリプト・ファイルは、リポジトリの外（作業用のフォルダ）に置く。
- 点検で見つけた秘密情報の値そのものは、plan・チャットに書かない（場所と種類のみを記載する）。

## 3. 点検の観点

観点ごとに次を行い、結果を「指摘あり（ai-review の ID）」「指摘なし」「未確認（理由）」のいずれかで記録する。

### 観点 1：テストに合格させるためだけの実装

| 点検すること | 方法の例 |
|---|---|
| テストで使った値（ニックネーム、数値、ID 等）や、テスト実行中かどうかの判定（`NODE_ENV`、`jest` 等）が、実装のコードに含まれていないか | テストファイルの値を `src/` で検索する（コメント中の例示は除く） |
| c1 の期待値と、テストのコメント `// Task-XXX 期待値N` が、タスクごとに 1 対 1 で対応しているか（c4 はテストケース `Test-XXX` と test-plan.md の対応） | 期待値の番号の数を照合する |
| テストの無効化（`.skip`、`.only`、`xit`、`test.todo`）、確認の弱い書き方（`expect(true)` のみ等）、テストが 0 件でも成功する設定がないか | 検索、`package.json`・`jest.config.js` の確認 |
| 期待値を変えずにテストのコードを変えた場合、その経緯が plan の実行結果に記録されているか | plan とコミットの差分の照合 |
| 計算の部分（外部に依存しない関数）が、テストの値以外でも正しく動くか | テストとは別の無作為なデータで、実装とは独立に書いた計算と突き合わせる（作業用のフォルダで実行する） |
| 静的解析・テストの設定を緩めていないか | ESLint のルールの無効化、`eslint-disable` のコメントの検索 |

### 観点 2：外部への意図しない通信

| 点検すること | 方法の例 |
|---|---|
| コードに通信の処理・外部の URL がないか（`fetch`、`XMLHttpRequest`、`UrlFetchApp`、`WebSocket`、外部の URL の `<script>`・`<link>` 等） | `src/`・`scripts/`・`tests/` の検索 |
| 依存ライブラリが、実装計画「2. 開発の前提」の定めのとおりか | `package.json` の照合 |
| マニフェストの権限・公開設定が、設計（Decision）のとおりで、必要以上に広くないか | `appsscript.json` と Decision の照合 |
| plan の実行結果に、計画外の通信（デプロイ、導入等）の記録がないか | plan の読解 |

### 観点 3：秘密情報の埋め込み

| 点検すること | 方法の例 |
|---|---|
| コード・テスト・ドキュメント・plan に、パスワード、API キー、トークン、スクリプト ID、スプレッドシート ID、メールアドレス等が書かれていないか | パターンによる検索 |
| 設定ファイル・認証情報が Git の管理対象外か | 観点 6 で点検する |
| 過去のコミットに秘密情報が残っていないか | 対象のコミットの `git log -p` をパターンで検索する |

### 観点 4：脆弱性

| 点検すること | 方法の例 |
|---|---|
| 画面で文字列が HTML として解釈される書き方（`innerHTML`、`outerHTML`、`insertAdjacentHTML`、`document.write`）がないか | 検索、該当箇所の読解 |
| 文字列をコードとして実行する書き方（`eval`、`new Function`、文字列の `setTimeout`）がないか | 検索 |
| シェルを介したコマンドの実行、利用者の入力をコマンドの引数に渡す箇所の検査の不足がないか | `child_process` の使用箇所の読解 |
| フォルダの外のファイルを参照・送信できる箇所がないか | ビルド・デプロイの処理の読解 |
| スプレッドシート等に書き込む文字列が、数式・別の型として解釈されないか | 書き込みの処理の読解 |
| 認証・認可の設定、エラーの文言・ログから、機密の情報が漏れないか | 設計書「7. 横断的な関心事」との照合 |
| 許容する基準を超える脆弱性が依存ライブラリにないか | `npm audit --audit-level=<実装計画の基準>` |

### 観点 5：工程の範囲

| 点検すること | 方法の例 |
|---|---|
| 対象工程のコミットに、他の工程の plan・成果物、計画外のファイルが含まれていないか | `git log --name-only` |
| 計画と異なる実装が、実装設計書の「計画との違い」（c4 はテスト報告書）に記録されているか | 照合 |

### 観点 6：除外設定と秘密情報の配置

#### 6-1. 除外設定の点検

リポジトリにある除外設定をすべて洗い出し（`ls -a` 等で、下表にない除外設定の有無も確認する）、それぞれ次を点検する。

| 除外設定 | 役割 | 点検すること |
|---|---|---|
| `.gitignore`（サブフォルダの `.gitignore`、`.git/info/exclude` を含む） | Git に含めない | 次がすべて除外されているか：認証情報（例：`.clasprc.json`）、プロジェクトの設定・ID を含むファイル（例：`.clasp.json`、`.clasp-*.json`）、環境変数のファイル（`.env*`）、鍵・証明書（`*.pem`、`*.key` 等）、個人用の設定（例：`.claude/settings.local.json`）、ビルドの出力（`dist/`）、依存ライブラリ（`node_modules/`）。パターンが、実際に使うファイル名・置き場所（実装設計書・セットアップ手順・スクリプトが案内するもの）と一致しているか。広すぎて、Git で管理すべきファイル（見本の `*.example`、ソース等）まで除外していないか。各行に理由のコメントがあるか |
| GAS に送るファイルの範囲（clasp の `rootDir`、`.claspignore`、ビルドの出力の対象） | GAS に送らない | 送る対象が `dist/<プロジェクト>/` の中の、実行に必要なファイル（`.js`・`.html`・`appsscript.json`）のみか。テスト・設定ファイル・秘密情報が送られないか |
| `.prettierignore`、ESLint の `ignores`、Jest の `roots`・`testPathIgnorePatterns` | 整形・静的解析・テストの対象外 | コード（`src/`、`scripts/`、`tests/`）が対象から外されていないか（外すと、問題が点検されないまま残る） |
| `.devcontainer/devcontainer.json` の `mounts` | ホストからコンテナに持ち込むもの | ホストの認証情報（`~/.ssh`、`~/.clasprc.json`、クラウドの認証情報等）を持ち込んでいないか |
| `.npmrc`、`.claude/settings.local.json` 等の個人・環境の設定 | 個人の設定・トークン | Git の管理対象になっていないか |

#### 6-2. 秘密情報の配置の合致性

| 点検すること | 方法の例 |
|---|---|
| 秘密情報・環境固有の値を置くと定めた場所（実装計画「2. 開発の前提」、実装設計書、セットアップ手順、スクリプトのエラーの文言が案内するファイル名・置き場所）が、すべて除外設定に当たるか | 案内されたファイル名ごとに `git check-ignore -v <パス>` |
| Git の管理対象のファイルに、除外設定に当たるものがないか（除外を設定する前にコミットされた秘密情報） | `git ls-files -ci --exclude-standard` |
| 実在する除外されたファイル・未追跡のファイルが、想定したもの（秘密情報のファイル、ビルドの出力、依存ライブラリ、個人の設定）のみか。点検・作業で作った一時的なファイルが残っていないか | `git status --ignored --short`、`git status --porcelain --untracked-files=all` |
| 除外されていないファイル（未追跡を含む）に秘密情報が含まれていないか | パターンによる検索 |
| 見本のファイル（`*.example` 等）の値が、見本の文字列（`<…を記入>` 等）のみか | 読解 |
| 秘密情報・環境固有の値を、コードではなく定めた場所（スクリプトプロパティ等）から読んでいるか | 設計・実装計画との照合、コードの読解 |
| GAS に送るファイル（`dist/`）に、秘密情報・テスト・設定ファイルが含まれていないか | `npm run build` の後に `dist/` の一覧と内容を確認する |

### 点検できない観点

- この環境で確認できない観点（ブラウザ・実機での見た目、デプロイ先での動作、アクセス制御等）は、推測で「指摘なし」としない。「未確認（理由）」として記録し、確認するテスト（c3 のテストケース等）があれば併記する。

## 4. 指摘の判定

- 指摘とするのは、観点 1〜6 に当たる事実が確認できたもののみとする。推測・一般論のみの懸念は指摘としない。
- 開発者が確定した事項（Question の回答、Decision、plan・実装設計書の「計画との違い」に記録済みの事項）は、それ自体を指摘としない。確定事項が新たな危険を生んでいる場合のみ、その事実を指摘とする。
- 既存の review 項目・ai-review 項目と同じ内容は、重複して指摘しない。
- 重要度は次のとおりとする。

| 重要度 | 基準 |
|---|---|
| 高 | 秘密情報の漏えい、認証・認可の回避、外部への意図しない送信が、通常の利用で起こりうる |
| 中 | 条件がそろうと、情報の漏えい・改ざん・誤った結果が起こりうる |
| 低 | 起こる条件が限られる（権限を持つ人の操作が必要等）、または影響が小さい |
| 参考 | 危険はないが、保守・運用の観点で開発者に知らせたほうがよい事実 |

## 5. plan への記録

1. 対象の plan ファイルの「9. レビュー指摘」の「AI からのレビュー指摘」に、指摘ごとに次の書式で追記する。ID は、その plan ファイル内の ai-review の次の連番とする。

```markdown
- [ ] **ai-review-001**：<指摘の要約>
  - 観点・重要度：<観点 1〜6 の名称>／<高・中・低・参考>
  - 事実：<場所（ファイル:行）、起こりうること、起こる条件>
  - 推奨：<直し方と根拠。根拠がない場合は「推奨なし（根拠資料なし）」>
  - 開発者判断：

  - AI対応内容：

  - AI確認結果：
```

2. 同じ欄の「最終レビューの実施記録」に、実施ごとに次の表を追記する。

```markdown
| 実施日時 | 観点 | 結果 |
|---|---|---|
| YYYY-MM-DD HH:MM | 1. テストに合格させるためだけの実装 | 指摘なし（<確認した内容の要約>） |
| YYYY-MM-DD HH:MM | 4. 脆弱性 | ai-review-001 |
| YYYY-MM-DD HH:MM | （未確認）ブラウザでの見た目 | 未確認（この環境にブラウザがない。Test-XXX で確認する） |
```

3. ステータスは「レビュー待ち」のまま変更しない。「1. 進捗」の「6. 成果物レビュー」に ☑ を付けない。
4. plan の「変更履歴」に、実施した点検と追記した ai-review 項目を記載する。
5. `plans/README.md` の該当工程の未対応のレビュー指摘の数（ai-review 項目の ☐ を含む）を更新する。

## 6. 報告

チャットで次を報告して停止する。

1. 点検した範囲（工程、ファイル、コミットの範囲）
2. 観点ごとの結果（指摘あり／指摘なし／未確認）
3. 追加した ai-review 項目の一覧（ID、要約、重要度）
4. 次に行うこと
   - ai-review 項目がある場合：各項目の「開発者判断」に「対応する」「対応しない」または指示（その他）を記入し、対象工程のスキル（`/c2-implement`、`/c4-test`）を実行する。「対応しない」の場合は理由を併記する
   - ai-review 項目がない場合：成果物をレビューし、指摘があれば「9. レビュー指摘」に review 項目を追記、指摘がなければ「1. 進捗」の「6. 成果物レビュー」に ☑ を付けて、対象工程のスキルを実行する
