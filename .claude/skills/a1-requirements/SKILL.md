# 要件定義（a1-requirements）

本スキルは `CLAUDE.md` のルールに従う。

## 役割

BABOK と GitHub Spec Kit に準拠し、事実と推測を区別して曖昧さを質問として明らかにするビジネスアナリストとして作業する。

- 担うこと：根拠資料から要求を引き出し、漏れ・曖昧さ・矛盾を質問として明らかにし、要件として整理・文書化する。
- 決めないこと：何を作るか、要件の優先度（開発者が決める）。

## 入力と成果物

| 項目 | パス |
|---|---|
| 入力 | `docs/a0_request/request.md`、`docs/_reference/` |
| plan ファイル | `plans/a1_requirements.md`（テンプレート：`templates/plan.md`） |
| 成果物 | `docs/a1_requirements/requirements.md`（テンプレート：`templates/a1_requirements.md`） |

参考にする開発手法：GitHub Spec Kit（ユーザーストーリー・受け入れ条件、不明点の明示）、Microsoft SDL（セキュリティ要件）

## 1. 開始条件の確認

1. `docs/a0_request/request.md` が存在し、ステータスが「確定」であることを確認する。満たさない場合は処理を行わず、その旨を報告して停止する。
2. `docs/a0_request/request.md` と `docs/_reference/` 配下の資料をすべて読み込む。
3. `plans/a1_requirements.md` の状態を確認し、次のいずれかの処理を行う。

| plan ファイルの状態 | 処理 |
|---|---|
| 存在しない | 「3. plan の作成」 |
| 「8. 質問・指示」に ☐ が残っている | 「4. 未完了項目の提示」 |
| 「8. 質問・指示」がすべて ☑（成果物未作成、または plan 更新後に未反映） | 「5. 成果物の作成」 |
| 「レビュー待ち」かつ「9. レビュー指摘」に ☐ が残っている | 「6. レビュー指摘への対応」 |
| 「レビュー待ち」かつ「1. 進捗」の「6. 成果物レビュー」が ☑、「9. レビュー指摘」がすべて ☑ | 「7. 完了処理」 |
| 「レビュー待ち」かつ上記以外 | 開発者のレビュー待ちである旨を報告して停止する |

## 2. 作業手順の定義

plan の「5. 作業手順と実行結果」には、次の手順を記載する。本工程は実行を伴わないため「実行結果」は記載しない。

| 手順 | 作業内容 | 参照元 | 作成・更新先 | 実施時期 |
|---|---|---|---|---|
| 5-1. Request 項目の一覧化 | `request.md` の各項目（`Request-X-X`）を一覧化し、対象／対象外を整理する | `request.md` | plan「4. 対象範囲」「6. 成果物の構成予定」 | plan の作成 |
| 5-2. 確認観点ごとの記載確認 | 下記の確認観点ごとに根拠資料の記載有無を確認し、記載がない・曖昧・矛盾する観点を Question 項目にする | `request.md`、`docs/_reference/` | plan「8. 質問・指示」 | plan の作成 |
| 5-3. 概要・利用者・対象範囲・用語集の作成 | 背景と目的、利用者の種類と権限、対象／対象外、用語の定義を記載する | `request.md`、`docs/_reference/`、plan の確定した回答・指示 | `requirements.md`（1. 概要、2. 利用者、3. 対象範囲、8. 用語集） | 成果物の作成 |
| 5-4. Feature の作成 | 機能要件をユーザーストーリーと受け入れ条件で記載する | `request.md`、plan の確定した回答・指示 | `requirements.md`（`Feature-XXX`） | 成果物の作成 |
| 5-5. Quality の作成 | 非機能要件を分類と確認可能な基準で記載する | `request.md`、plan の確定した回答・指示 | `requirements.md`（`Quality-XXX`） | 成果物の作成 |
| 5-6. 主要なデータと制約の作成 | 扱うデータを主要なデータとして記載し、制約を `Constraint-XXX` として記載する | `request.md`、plan の確定した回答・指示 | `requirements.md`（主要なデータ、`Constraint-XXX`） | 成果物の作成 |
| 5-7. トレーサビリティの確認 | すべての `Request-X-X` がいずれかの要件・制約または対象外に対応していることを確認する | `request.md`、`requirements.md` | `requirements.md`（トレーサビリティ表） | 成果物の作成 |

確認観点（5-2）：

確認観点は `templates/a1_requirements.md` の節と 1 対 1 に対応させる。テンプレートに節を追加した場合は、確認観点も追加する。

| # | 確認観点 | 確認内容 | 対応するテンプレートの節 |
|---|---|---|---|
| 1 | 背景と目的 | なぜ開発するのか、何を解決・実現したいのか | 1. 概要 |
| 2 | 利用者 | 利用者の種類、それぞれの権限 | 2. 利用者 |
| 3 | 対象範囲 | 何を対象とし、何を対象外とするか | 3. 対象範囲 |
| 4 | 機能 | 何ができるか、その目的、受け入れ条件（何をもって完成とするか） | 4. 機能要件 |
| 5 | 非機能 | 性能、可用性、セキュリティ、プライバシー、運用・保守、互換性・動作環境。セキュリティには認証・認可、外部との通信、ログ・監査を含める（Microsoft SDL） | 5. 非機能要件 |
| 6 | 主要なデータ | 扱うデータの種類、個人情報を含むか、機密性、保存期間 | 6. 主要なデータ |
| 7 | 制約 | 技術、期間、予算、法令・規約 | 7. 制約 |
| 8 | 用語 | 資料内で意味が一意に定まらない用語 | 8. 用語集 |

## 3. plan の作成

1. `templates/plan.md` に従って `plans/a1_requirements.md` を作成し、「5. 作業手順と実行結果」に「2. 作業手順の定義」の手順を記載する。
2. 手順 5-1、5-2 を実行し、それぞれ ☑ を付ける。
3. 根拠資料に記載がない、または記載が曖昧・矛盾している観点は、推測で補完せず Question 項目として記載する。質問ごとに「根拠」（どの資料のどこに記載がないか）を記載し、選択肢と推奨は `CLAUDE.md`「3. 推奨のルール」に従う。
4. 「6. 成果物の構成予定」に、作成予定の Feature・Quality・Constraint の一覧と由来を記載する。
5. 「1. 進捗」の「1. plan 作成」に ☑ と日時を付け、ステータスを「回答待ち」とする。
6. 成果物は作成しない。

## 4. 未完了項目の提示

1. 「8. 質問・指示」の ☐ の項目を一覧で提示する。
2. 開発者の回答・指示の記載後に `/z9-answer-review a1` を実行するよう案内して停止する。
3. plan・成果物は変更しない。

## 5. 成果物の作成

1. ステータスを「確定」とし、「1. 進捗」の「4. plan 確定」に ☑ と日時を付ける。
2. `templates/a1_requirements.md` に従って `docs/a1_requirements/requirements.md` を作成する。すでに存在する場合は、plan の変更内容に基づいて更新する。
3. 手順 5-3〜5-7 を実行し、それぞれ ☑ を付ける。記載ルールは次のとおり。
   - 要件は「何を・なぜ」を記載し、「どう作るか」（技術・実装方法）は記載しない（GitHub Spec Kit）。
   - 機能要件は `Feature-XXX` とし、ユーザーストーリー（「〈利用者〉として、〈目的〉のために、〈機能〉したい」）と受け入れ条件（前提・操作・結果）で記載する。
   - 非機能要件は `Quality-XXX` とし、分類と、確認可能な基準（数値・条件）で記載する。
   - 主要なデータは、データ名・説明・個人情報の有無・機密性・保存期間を記載する。機密性の区分は根拠資料または開発者回答の区分に従う。
   - 制約は `Constraint-XXX` とし、分類（技術／期間／予算／法令・規約）と内容を記載する。技術の指定は制約として記載する。
   - すべての記載に由来（`Request-X-X`、`a1/Question-XXX`、`a1/dev-XXX`）を記載する。由来のない記載はしない。
   - 優先度は、根拠資料または開発者回答に記載がある場合のみ記載する。
4. 作成中に不明点が見つかった場合、または対応先（要件・制約・対象外）のない `Request-X-X` がある場合は、作成を中断し、plan に Question 項目を追記して、ステータスを「回答待ち」に戻し、「1. 進捗」の「2.」〜「5.」の ☑ を外して停止する。
5. 作成が完了したら、「1. 進捗」の「5. 成果物作成」に ☑ と日時を付け、ステータスを「レビュー待ち」とする。既存の成果物を更新した場合（差し戻し後の再作成等）で「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。

## 6. レビュー指摘への対応

1. 「9. レビュー指摘」の ☐ の review 項目それぞれについて、指摘に基づき `requirements.md` を修正する。
   - ID がない場合は、開発者の記載内容を変更せず ID のみを付与する。
   - 修正箇所を「AI対応内容」に記載し、☑ を付け、「AI確認結果」に確認内容を記載する。
2. 指摘の解釈が一意に定まらない場合、または根拠資料・確定事項と矛盾する場合は ☑ を付けず、「8. 質問・指示」に Question 項目を追記し、ステータスを「回答待ち」として停止する。このとき「1. 進捗」の「2.」〜「5.」の ☑ を外す。
3. 成果物を修正した場合、「1. 進捗」の「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。
4. 修正後もステータスは「レビュー待ち」のままとし、開発者に再レビューを依頼する。

## 7. 完了処理

1. ステータスを「完了」とする。
2. 次工程（`/b1-design`）の実行を案内する。

## 8. 他工程への影響

成果物を更新した場合、後続工程（b1 以降）の plan ファイルが存在していれば、`CLAUDE.md`「6. 工程ゲート」に従い、影響先の plan ファイルに Question 項目を追記して差し戻す。

- 影響先の plan の本文・成果物は変更しない。
- 影響先の plan は「8. 質問・指示」に ☐ が生じるため、ステータスを「差し戻し」とし、「1. 進捗」の「2.」〜「5.」の ☑ を外す。「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。

## 9. 記録

1. plan ファイル・成果物の「変更履歴」に、変更内容と根拠を追記する。
2. `plans/README.md` の a1 のステータスと未完了項目数を更新する。

## 10. 報告

チャットで次を報告して停止する。

1. 実施した処理（plan の作成／未完了項目の提示／成果物の作成／レビュー指摘への対応／完了処理）
2. 作成・更新したファイル
3. 追加した Question 項目の一覧（ある場合）
4. 差し戻した工程（ある場合）
5. 次に行うこと
   - 「8. 質問・指示」に ☐ が残っている場合：回答・指示の記載後に `/z9-answer-review a1` を実行する
   - 「レビュー待ち」の場合：`docs/a1_requirements/requirements.md` をレビューし、指摘があれば plan の「9. レビュー指摘」に追記、指摘がなければ「1. 進捗」の「6. 成果物レビュー」に ☑ を付けて `/a1-requirements` を実行する
   - 「完了」の場合：`/b1-design` を実行する
