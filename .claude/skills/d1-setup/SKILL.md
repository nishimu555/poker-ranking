# セットアップ手順（d1-setup）

本スキルは `CLAUDE.md` のルールに従う。

## 役割

Microsoft Engineering Playbook に準拠し、手順を実際に試して確かめる DevOps エンジニア兼テクニカルライターとして作業する。

- 担うこと：開発環境の構築・テストの実行・デプロイの手順を、読者が迷わず再現できるように記載し、実際に試して結果を記録する。
- 決めないこと：手順書の対象読者、手順書に含める範囲、対象とする環境。開発者が決める。

## 入力と成果物

| 項目 | パス |
|---|---|
| 入力 | `docs/c2_implement/implementation-design.md`、`docs/c1_implementation-plan/implementation-plan.md`（2. 開発の前提）、`docs/c3_test-plan/test-plan.md`（6. 開発者が実行するテストの手順）、`docs/c4_test/test-report.md`、`src/`、`tests/`、設定ファイル |
| plan ファイル | `plans/d1_setup.md`（テンプレート：`templates/plan.md`） |
| 成果物 | `docs/d1_setup/setup-guide.md`（テンプレート：`templates/d1_setup-guide.md`） |
| 成果物 | `README.md`（リポジトリ直下） |

参考にする開発手法：Microsoft Engineering Playbook（ドキュメント）

## 1. 開始条件の確認

1. `plans/c4_test.md` のステータスが「完了」であることを確認する。満たさない場合は処理を行わず、その旨を報告して停止する。
2. 入力を読み込む。`src/`・`tests/` は `implementation-design.md` を読んだうえで、必要なファイルのみを読む。
3. `plans/d1_setup.md` と `docs/d1_setup/setup-guide.md` の状態を確認し、上から順に判定して最初に該当する処理を行う。

| 状態 | 処理 |
|---|---|
| plan ファイルが存在しない | 「3. plan の作成」 |
| 「8. 質問・指示」に ☐ が残っている | 「4. 未完了項目の提示」 |
| 「8. 質問・指示」がすべて ☑、かつ手順書が未作成または plan 更新後に未反映 | 「5. 手順書の作成と検証」 |
| 手順書の検証の記録に、実行者が開発者で結果が空欄の手順がある | 「6. 開発者の検証結果待ち」 |
| 検証の記録がすべて記載済みで、確認が未実施 | 「7. 検証結果の確認」 |
| 「レビュー待ち」かつ「9. レビュー指摘」に ☐ が残っている | 「8. レビュー指摘への対応」 |
| 「レビュー待ち」かつ「1. 進捗」の「6. 成果物レビュー」が ☑、「9. レビュー指摘」がすべて ☑ | 「9. 完了処理」 |
| 「レビュー待ち」かつ上記以外 | 開発者のレビュー待ちである旨を報告して停止する |

## 2. 作業手順の定義

plan の「5. 作業手順と実行結果」には、次の手順を記載する。本工程は実行を伴うため、各手順に「実行結果」を記載する。

| 手順 | 作業内容 | 参照元 | 作成・更新先 |
|---|---|---|---|
| 5-1. 実装設計書とコードの照合 | `implementation-design.md` のディレクトリ構成・ファイル一覧が、`src/`・`tests/` と一致していることを確認する | `implementation-design.md`、`src/`、`tests/` | plan の実行結果 |
| 5-2. 必要な情報の一覧化 | 必要なツールとバージョン、設定ファイル、環境変数、秘密情報の扱い、デプロイの方法を一覧化する | 入力すべて | plan「4. 対象範囲」「6. 成果物の構成予定」 |
| 5-3. 手順書の作成 | 確定した対象読者・範囲に従って手順書と `README.md` を作成する | 入力すべて、plan の確定した回答・指示 | `setup-guide.md`、`README.md` |
| 5-4. 手順の検証（AI） | 実行者が AI の手順を、下記「検証の方法」に従って実際に試す | `setup-guide.md` | `setup-guide.md`（8. 検証の記録） |
| 5-5. 開発者の検証結果の確認 | 開発者が記載した検証結果を確認する | `setup-guide.md`（8. 検証の記録） | `setup-guide.md`（8. 検証の記録） |

## 3. plan の作成

1. `templates/plan.md` に従って `plans/d1_setup.md` を作成し、「5. 作業手順と実行結果」に「2. 作業手順の定義」の手順を記載する。
2. 手順 5-1、5-2 を実行し、それぞれ ☑ と実行結果を記載する。実装設計書とコードが一致しない場合は、c2 の plan に Question 項目を追記して差し戻す（「11. 他工程への影響」）。
3. 次の確認観点ごとに根拠資料の記載有無を確認し、記載がない・曖昧・矛盾する観点は Question 項目として記載する。

| # | 確認観点 | 確認内容 | 対応するテンプレートの節 |
|---|---|---|---|
| 1 | 対象読者と範囲 | 手順書の対象読者（開発者、運用担当者、利用者等）、含める範囲（開発環境の構築、デプロイ、運用、利用方法等） | 1. 概要 |
| 2 | 前提 | 必要なツールとバージョン、OS、必要なアカウント・権限、検証環境（一時フォルダ／コンテナ） | 2. 前提 |
| 3 | 開発環境の構築 | 依存ライブラリの導入方法、設定ファイル・環境変数の作成方法 | 3. 開発環境の構築 |
| 4 | テストの実行 | テストの実行コマンド、ローカルで実行できないテストの扱い | 4. テストの実行 |
| 5 | デプロイ | デプロイ先、デプロイの方法、デプロイ後の確認方法 | 5. デプロイ |
| 6 | 秘密情報の扱い | 認証情報・API キー等の入手方法、保管場所、Git の管理対象外であること | 6. 秘密情報の扱い |

   - 対象読者と範囲は AI が決めず、必ず Question 項目で開発者に確認する。推奨は「開発環境の構築」と「デプロイ」を含めることとし、根拠（Microsoft Engineering Playbook のドキュメントの考え方）を記載する。
4. 「1. 進捗」の「1. plan 作成」に ☑ と日時を付け、ステータスを「回答待ち」とする。
5. 手順書は作成しない。

## 4. 未完了項目の提示

1. 「8. 質問・指示」の ☐ の項目を一覧で提示する。
2. 開発者の回答・指示の記載後に `/z9-answer-review d1` を実行するよう案内して停止する。
3. plan・成果物は変更しない。

## 5. 手順書の作成と検証

1. ステータスが「確定」でない場合は「確定」とし、「1. 進捗」の「4. plan 確定」に ☑ と日時を付ける。
2. 手順 5-3：`templates/d1_setup-guide.md` に従って `docs/d1_setup/setup-guide.md` を作成する（存在する場合は plan の変更内容に基づいて更新する）。記載ルールは次のとおり。
   - 手順は番号付きで、1 手順につき 1 操作とし、実行するコマンドと、成功したことを確認する方法（期待される出力等）を記載する。
   - 秘密情報そのものは記載せず、入手方法・保管場所・扱い方のみを記載する。
   - すべての記載に由来（`implementation-plan.md` 2. 開発の前提、`Decision-XXXX`、`d1/Question-XXX` 等）を記載する。由来のない記載はしない。
   - 各手順に実行者（AI／開発者）を定め、「8. 検証の記録」に一覧化する。
3. 手順 5-3：リポジトリ直下に `README.md` を作成・更新する。記載するのは、プロジェクトの概要（`requirements.md` 1. 概要の要約）と、手順書・主要な成果物へのリンクのみとする。
4. 手順 5-4：実行者が AI の手順を検証し、結果を「8. 検証の記録」に記載する。
5. 実行者が開発者の手順で結果が空欄のものがあれば「6. 開発者の検証結果待ち」、なければ「7. 検証結果の確認」に進む。

### 検証の方法

- 開発者の PC の環境を変更しない。
- リポジトリを一時フォルダ（セッションの作業用フォルダ等）に複製し、何もない状態から手順どおりに開発環境の構築・テストの実行を試す。
- 必要な場合は、コンテナ（`.devcontainer/` または手順書の対象環境に合わせたコンテナ）を検証環境として使う。コンテナを使うかどうかは、plan の Question 項目で開発者に確認する（例：PC にない実行環境が必要な場合、対象読者の環境を再現する必要がある場合）。コンテナの起動は開発者が行う（`guide/04_sandbox.md` 参照）。検証環境の種類は「8. 検証の記録」の検証環境の欄に記載する。
- PC 全体に影響する操作（`brew install` 等のグローバルなインストール、OS の設定変更）は実行せず、バージョン確認コマンド等で導入済みかどうかのみを確認し、その旨を記録する。
- アカウント・認証情報・デプロイが必要な手順は、実行者を開発者とする。
- 手順どおりに実行して失敗した場合は、手順書を修正して再度試す。修正内容と、失敗した事実（エラー内容）を記録する。手順書の修正で解消できない場合（コードの不具合等）は、c2 の plan に Question 項目を追記して差し戻す。
- 原因を推測で記載しない。

## 6. 開発者の検証結果待ち

1. 結果が空欄の、実行者が開発者の手順を一覧で提示する。
2. 手順書に従って試し、結果（成功／失敗、実施日、失敗時の状況）を `docs/d1_setup/setup-guide.md`「8. 検証の記録」の該当欄に記載したうえで `/d1-setup` を実行するよう案内して停止する。
3. 開発者の結果欄は変更しない。空欄の手順は「未検証」として扱う。

## 7. 検証結果の確認

1. 手順 5-5：開発者が記載した結果を確認する。形式が不明確な場合は Question 項目で確認する。
2. すべての手順が成功している場合：「1. 進捗」の「5. 成果物作成」に ☑ と日時を付け、ステータスを「レビュー待ち」とする。既存の成果物を更新した場合で「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。
3. 失敗した手順がある場合：失敗の事実を示し、手順書の修正で対応できる場合は修正して、該当手順の再検証を求める（結果欄は新しい行として追記する）。コードの修正が必要な場合は c2 の plan に Question 項目を追記して差し戻す。

## 8. レビュー指摘への対応

1. 「9. レビュー指摘」の ☐ の review 項目それぞれについて、指摘に基づき手順書・`README.md` を修正する。
   - ID がない場合は、開発者の記載内容を変更せず ID のみを付与する。
   - 修正した手順は再度検証する（実行者が開発者の手順は、再検証を依頼する）。
   - 修正箇所を「AI対応内容」に記載し、☑ を付け、「AI確認結果」に確認内容を記載する。
2. 指摘の解釈が一意に定まらない場合、または根拠資料・確定事項と矛盾する場合は ☑ を付けず、「8. 質問・指示」に Question 項目を追記し、ステータスを「回答待ち」として停止する。このとき「1. 進捗」の「2.」〜「5.」の ☑ を外す。
3. 成果物を修正した場合、「1. 進捗」の「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。
4. 修正後もステータスは「レビュー待ち」のままとし、開発者に再レビューを依頼する。

## 9. 完了処理

1. ステータスを「完了」とする。
2. 全工程が完了した旨を報告する。

## 10. 記録

1. plan ファイル・手順書の「変更履歴」に、変更内容と根拠を追記する。
2. `plans/README.md` の d1 のステータスと未完了項目数を更新する。

## 11. 他工程への影響

- 実装設計書とコードの不一致、コードの不具合は c2、実装計画の開発の前提・デプロイの方法の不足は c1、テスト手順の不足は c3 の plan ファイルに Question 項目を追記して差し戻す。
- `CLAUDE.md`「6. 工程ゲート」に従う。影響先の plan の本文・成果物は変更しない。影響先の plan のステータスを「差し戻し」とし、「1. 進捗」の「2.」〜「5.」の ☑ を外す。「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。

## 12. 報告

チャットで次を報告して停止する。

1. 実施した処理（plan の作成／未完了項目の提示／手順書の作成と検証／開発者の検証結果待ち／検証結果の確認／レビュー指摘への対応／完了処理）
2. 作成・更新したファイル
3. 検証の結果（実行者別：成功／失敗／未検証の件数、失敗の事実）
4. 追加した Question 項目の一覧（ある場合）
5. 差し戻した工程（ある場合）
6. 次に行うこと
   - 開発者の検証が未実施の場合：検証する手順の一覧、結果の記載先（`setup-guide.md`「8. 検証の記録」）、記載後に `/d1-setup` を実行すること
   - 「8. 質問・指示」に ☐ が残っている場合：回答・指示の記載後に `/z9-answer-review d1` を実行する
   - 「レビュー待ち」の場合：`docs/d1_setup/setup-guide.md` と `README.md` をレビューし、指摘があれば plan の「9. レビュー指摘」に追記、指摘がなければ「1. 進捗」の「6. 成果物レビュー」に ☑ を付けて `/d1-setup` を実行する
