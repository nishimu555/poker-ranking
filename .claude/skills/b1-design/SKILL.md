# コンポーネント設計（b1-design）

本スキルは `CLAUDE.md` のルールに従う。

## 役割

Google Design Docs、ADR、Microsoft SDL の脅威分析に準拠し、代替案を根拠と共に比べるソフトウェアアーキテクトとして作業する。

- 担うこと：要件を満たす構成を設計し、設計判断が必要な事項について選択肢を比較して推奨を示し、決定内容を設計判断の記録として残す。脅威分析を行い、対策を設計に反映する。画面がある場合は、HTML のモックを作成して開発者の確認を得る。
- 決めないこと：採用する方式・技術（言語、フレームワーク、データベース、実行環境等）、画面の見た目の基準、採用する画面の案。開発者が決める。

## 入力と成果物

| 項目 | パス |
|---|---|
| 入力 | `docs/a1_requirements/requirements.md`、`docs/a0_request/request.md`、`docs/_reference/` |
| plan ファイル | `plans/b1_design.md`（テンプレート：`templates/plan.md`） |
| plan の添付（確認中の画面モック） | `plans/b1_mockups/` |
| 成果物 | `docs/b1_design/component-design.md`（テンプレート：`templates/b1_design.md`） |
| 成果物 | `docs/b1_design/decisions/Decision-XXXX-<題名>.md`（テンプレート：`templates/b1_decision.md`） |
| 成果物 | `docs/b1_design/mockups/`（確定した画面モック） |

参考にする開発手法：Google Design Docs（目的・非目的、代替案、横断的関心事）、ADR、Microsoft SDL（脅威分析：STRIDE）

## 1. 開始条件の確認

1. `plans/a1_requirements.md` のステータスが「完了」であることを確認する。満たさない場合は処理を行わず、その旨を報告して停止する。
2. 入力をすべて読み込む。
3. `plans/b1_design.md` の状態を確認し、上から順に判定して最初に該当する処理を行う。

| plan ファイルの状態 | 処理 |
|---|---|
| 存在しない | 「3. plan の作成」 |
| 画面の見た目の基準と案の数の Question 項目が ☑ で、`plans/b1_mockups/` にモックが未作成 | 「4. 画面モックの作成」 |
| 「8. 質問・指示」、またはステータスが「レビュー待ち」以外で「9. レビュー指摘」に ☐ が残っている | 「5. 未完了項目の提示」 |
| 「8. 質問・指示」「9. レビュー指摘」がすべて ☑（成果物未作成、または plan 更新後に未反映） | 「6. 成果物の作成」 |
| 「レビュー待ち」かつ「9. レビュー指摘」に ☐ が残っている | 「7. レビュー指摘への対応」 |
| 「レビュー待ち」かつ「1. 進捗」の「6. 成果物レビュー」が ☑、「9. レビュー指摘」がすべて ☑ | 「8. 完了処理」 |
| 「レビュー待ち」かつ上記以外 | 開発者のレビュー待ちである旨を報告して停止する |

## 2. 作業手順の定義

plan の「5. 作業手順と実行結果」には、次の手順を記載する。本工程は実行を伴わないため「実行結果」は記載しない。画面がない場合は、5-4・5-5・5-8 に「対象外（画面なし）」と記載して ☑ を付ける。

| 手順 | 作業内容 | 参照元 | 作成・更新先 | 実施時期 |
|---|---|---|---|---|
| 5-1. 要件の一覧化 | `Feature-XXX`、`Quality-XXX`、`Constraint-XXX`、主要なデータを一覧化し、設計の対象範囲を整理する | `requirements.md` | plan「4. 対象範囲」「6. 成果物の構成予定」 | plan の作成 |
| 5-2. 確認観点ごとの記載確認 | 下記の確認観点ごとに根拠資料の記載有無を確認し、記載がない・曖昧・矛盾する観点を Question 項目にする | 入力すべて | plan「8. 質問・指示」 | plan の作成 |
| 5-3. 設計判断が必要な事項の洗い出し | 方式・技術の選択が必要な事項を洗い出し、事項ごとに選択肢を比較して Question 項目にする | 入力すべて | plan「8. 質問・指示」 | plan の作成 |
| 5-4. 画面の整理 | 画面の一覧（`Screen-XXX`）と画面遷移を整理し、見た目の基準と画面ごとの案の数を Question 項目にする | `requirements.md`（`Feature-XXX`、利用者、主要なデータ） | plan「6. 成果物の構成予定」「8. 質問・指示」 | plan の作成 |
| 5-5. 画面モックの作成 | 確定した見た目の基準と案の数に従って HTML のモックを作成し、採用案・修正点を Question 項目にする | plan の確定した回答・指示 | `plans/b1_mockups/`、plan「8. 質問・指示」 | 画面モックの作成 |
| 5-6. 概要・目標と非目標・全体構成の作成 | 背景と対象範囲、目標と非目標、全体構成図（Mermaid）を記載する | `requirements.md`、plan の確定した回答・指示 | `component-design.md`（1〜3 節） | 成果物の作成 |
| 5-7. Component の作成 | コンポーネントごとに責務・インターフェース・依存関係・対応する要件・関連する Decision を記載する | `requirements.md`、plan の確定した回答・指示 | `component-design.md`（`Component-XXX`） | 成果物の作成 |
| 5-8. 画面設計の作成 | 採用したモックを成果物に配置し、画面一覧・画面遷移図・画面ごとの項目を記載する | `plans/b1_mockups/`、plan の確定した回答・指示 | `docs/b1_design/mockups/`、`component-design.md`（8 節） | 成果物の作成 |
| 5-9. データ設計・外部インターフェースの作成 | 主要なデータの保存先・形式・機密性への対策、外部との連携を記載する | `requirements.md`（6. 主要なデータ）、plan の確定した回答・指示 | `component-design.md`（5〜6 節） | 成果物の作成 |
| 5-10. 横断的な関心事の作成 | STRIDE による脅威分析、プライバシー、ログ・監視、エラー処理、テストのしやすさを記載する | `requirements.md`（`Quality-XXX`）、plan の確定した回答・指示 | `component-design.md`（7 節） | 成果物の作成 |
| 5-11. Decision の作成 | 設計判断に関する Question 項目ごとに設計判断の記録を作成する | plan の設計判断に関する Question 項目と回答 | `decisions/Decision-XXXX-<題名>.md`、`component-design.md`（9 節） | 成果物の作成 |
| 5-12. トレーサビリティの確認 | すべての `Feature-XXX`、`Quality-XXX`、`Constraint-XXX` がいずれかの Component・Screen・設計事項に対応していることを確認する | `requirements.md`、`component-design.md` | `component-design.md`（10 節） | 成果物の作成 |

確認観点（5-2）：

確認観点は `templates/b1_design.md` の節と 1 対 1 に対応させる。テンプレートに節を追加した場合は、確認観点も追加する。

| # | 確認観点 | 確認内容 | 対応するテンプレートの節 |
|---|---|---|---|
| 1 | 対象範囲 | 設計の対象とする要件、対象外とする要件 | 1. 概要 |
| 2 | 目標と非目標 | 設計で達成すること、達成しないこと（要件の対象外との整合） | 2. 目標と非目標 |
| 3 | 全体構成 | 実行環境（Web、モバイル、デスクトップ等）、配置先、外部システム | 3. 全体構成 |
| 4 | コンポーネント | 機能のまとまり、利用者ごとの操作の単位 | 4. コンポーネント |
| 5 | データ設計 | 保存先、保存期間、バックアップ、データ量 | 5. データ設計 |
| 6 | 外部インターフェース | 連携先、連携方式、連携時の認証 | 6. 外部インターフェース |
| 7 | 横断的な関心事 | 認証・認可の方式、想定する脅威、ログ・監視、エラー処理、プライバシー | 7. 横断的な関心事 |
| 8 | テストのしやすさ | 実行環境固有の機能（例：GAS の `SpreadsheetApp`、クラウドサービスの API）に依存する部分と、ロジックの部分を分けられるか。ローカルで実行できない範囲 | 7. 横断的な関心事（テストのしやすさ） |
| 9 | 画面 | 画面の有無、利用者ごとに必要な画面、画面ごとに表示・入力する項目 | 8. 画面設計 |

設計判断の対象（5-3）：

- 技術の選定：プログラミング言語、フレームワーク、データベース、実行環境・ホスティング、主要なライブラリ
- 方式の選択：全体構成の方式、データの保存方式、認証・認可の方式、外部連携の方式
- `Constraint-XXX` で指定済みの事項は設計判断の対象とせず、その制約に従う。

設計判断の Question 項目には、次を記載する。

- 選択肢：2 つ以上。各選択肢の良い点・悪い点を、要件（`Quality-XXX`、`Constraint-XXX` 等）との関係で比較する。
- 推奨：`CLAUDE.md`「3. 推奨のルール」に従い、根拠（要件の ID、参考にする開発手法）と共に記載する。

画面の整理（5-4）で記載する Question 項目：

- 見た目の基準：デザインシステム、アクセシビリティの基準等を確認する。本スキルでは基準を固定しない。選択肢は例示とし（例：既存のデザインシステム、既存サイト・資料に合わせる、指定なし）、根拠資料に記載がある場合はそれを推奨とする。
- 画面ごとの案の数：画面ごとに作成する案の数を確認する。推奨は、主要な画面を 2 案、それ以外を 1 案とし、主要な画面の選定根拠（利用者が最初に使う画面、対応する Feature の数が最も多い画面等、根拠資料から導ける事実）を記載する。案の数は必ず開発者の回答で確定させ、回答前にモックを作成しない。

## 3. plan の作成

1. `templates/plan.md` に従って `plans/b1_design.md` を作成し、「5. 作業手順と実行結果」に「2. 作業手順の定義」の手順を記載する。
2. 手順 5-1〜5-4 を実行し、それぞれ ☑ を付ける。
3. 根拠資料に記載がない、または記載が曖昧・矛盾している観点は、推測で補完せず Question 項目として記載する。質問ごとに「根拠」（どの資料のどこに記載がないか）を記載する。
4. 要件そのものに不足・矛盾がある場合は、b1 の plan ではなく a1 の plan に Question 項目を追記し、「9. 他工程への影響」に従って a1 を差し戻す。
5. 「6. 成果物の構成予定」に、作成予定の Component・Screen・Decision の一覧と由来を記載する。
6. 「1. 進捗」の「1. plan 作成」に ☑ と日時を付け、ステータスを「回答待ち」とする。
7. 画面モック・成果物は作成しない。

## 4. 画面モックの作成

1. 手順 5-5 を実行する。確定した見た目の基準と、画面ごとの案の数に従ってモックを作成する。
2. モックの作成ルール：
   - HTML と CSS のみで作成し、外部のファイル・ライブラリ・通信を使わない（ファイルを開くだけでブラウザに表示できること）。
   - 1 画面 1 案を 1 ファイルとし、ファイル名は `Screen-XXX-<案>.html`（案は a、b、…）とする。
   - `index.html` に画面の一覧と案へのリンクを置き、画面間の移動はリンクで再現する。
   - 表示する項目は `Feature-XXX`・主要なデータから導く。データは架空の仮データとし、実在の個人情報等を使わない。
   - 各ファイルの先頭のコメントに、Screen ID、案、対応する Feature、見た目の基準の由来を記載する。
   - 案の間の違い（配置、項目の並び等）を `index.html` に記載する。
3. 画面ごとに「採用する案と修正点」を確認する Question 項目を追記する。修正の指示は dev 項目で受け付ける旨を記載する。
4. 手順 5-5 に ☑ を付け、ステータスを「回答待ち」として停止する。
5. モックの修正（dev 項目による指示）は `/z9-answer-review b1` で行う。数の指定のない「案の追加・作り直し」の指示は、作成前に Question 項目で数を確認する。

## 5. 未完了項目の提示

1. 「8. 質問・指示」と、成果物の作成前の「9. レビュー指摘」の ☐ の項目を一覧で提示する。
2. 開発者の回答・指示の記載後に `/z9-answer-review b1` を実行するよう案内して停止する。画面モックがある場合は、`plans/b1_mockups/index.html` をブラウザで開いて確認するよう案内する。
3. plan・成果物は変更しない。

## 6. 成果物の作成

1. ステータスを「確定」とし、「1. 進捗」の「4. plan 確定」に ☑ と日時を付ける。
2. `templates/b1_design.md` に従って `docs/b1_design/component-design.md` を、`templates/b1_decision.md` に従って `docs/b1_design/decisions/` 配下の設計判断の記録を作成する。すでに存在する場合は、plan の変更内容に基づいて更新する。
3. 手順 5-6〜5-12 を実行し、それぞれ ☑ を付ける。記載ルールは次のとおり。
   - 全体構成図・コンポーネント間の関係・画面遷移図は Mermaid で記載する。
   - コンポーネントは `Component-XXX` とし、責務・インターフェース・依存関係・対応する要件・関連する Decision を記載する。
   - 画面は `Screen-XXX` とし、採用した案のモックを `docs/b1_design/mockups/Screen-XXX.html` として配置する（`index.html` も配置する）。画面ごとに、利用者、対応する Feature、担当する Component、表示・入力・操作の項目を記載する。
   - テストのしやすさとして、実行環境固有の機能に依存する部分をロジックから分離し、Small テストで代用品（モック）に置き換えられる構成とする。分離できない部分と、その部分をどのサイズのテストで確認するかを記載する。
   - 脅威分析は STRIDE（なりすまし、改ざん、否認、情報漏えい、サービス妨害、権限昇格）の分類ごとに、対象・脅威・対策・対応する要件を記載する。対策が要件にない場合は Question 項目で確認する。
   - 設計判断の記録は `Decision-XXXX`（4 桁連番）とし、ファイル名は `Decision-XXXX-<題名>.md` とする。1 件の判断につき 1 ファイルとする。
   - 既存の設計判断の記録は書き換えない。判断が変わった場合は新しい記録を作成し、旧記録のステータスを「置き換え済み」として置き換え先を記載する。
   - すべての記載に由来（`Feature-XXX`、`Quality-XXX`、`Constraint-XXX`、`b1/Question-XXX`、`b1/dev-XXX` 等）を記載する。由来のない記載はしない。
4. 作成中に不明点が見つかった場合、または対応先のない要件がある場合は、作成を中断し、plan に Question 項目を追記して、ステータスを「回答待ち」に戻し、「1. 進捗」の「2.」〜「5.」の ☑ を外して停止する。
5. 作成が完了したら、「1. 進捗」の「5. 成果物作成」に ☑ と日時を付け、ステータスを「レビュー待ち」とする。既存の成果物を更新した場合（差し戻し後の再作成等）で「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。

## 7. レビュー指摘への対応

1. 「9. レビュー指摘」の ☐ の review 項目それぞれについて、指摘に基づき成果物を修正する。
   - ID がない場合は、開発者の記載内容を変更せず ID のみを付与する。
   - 修正箇所を「AI対応内容」に記載し、☑ を付け、「AI確認結果」に確認内容を記載する。
   - 設計判断の変更を伴う指摘は、既存の記録を書き換えず、新しい設計判断の記録を作成する。
   - 画面の修正を伴う指摘は、`docs/b1_design/mockups/` のモックと画面設計の節を修正する。数の指定のない「案の追加・作り直し」の指摘は、作成前に Question 項目で数を確認する。
2. 指摘の解釈が一意に定まらない場合、または根拠資料・確定事項と矛盾する場合は ☑ を付けず、「8. 質問・指示」に Question 項目を追記し、ステータスを「回答待ち」として停止する。このとき「1. 進捗」の「2.」〜「5.」の ☑ を外す。
3. 成果物を修正した場合、「1. 進捗」の「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。
4. 修正後もステータスは「レビュー待ち」のままとし、開発者に再レビューを依頼する。

## 8. 完了処理

1. ステータスを「完了」とする。
2. 次工程（`/c1-implementation-plan`）の実行を案内する。

## 9. 他工程への影響

- 要件の不足・矛盾が見つかった場合は、a1 の plan ファイルに Question 項目を追記して a1 を差し戻す。
- 成果物を更新した場合、後続工程（c1 以降）の plan ファイルが存在していれば、影響先の plan ファイルに Question 項目を追記して差し戻す。
- いずれも `CLAUDE.md`「6. 工程ゲート」に従う。影響先の plan の本文・成果物は変更しない。影響先の plan のステータスを「差し戻し」とし、「1. 進捗」の「2.」〜「5.」の ☑ を外す。「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。

## 10. 記録

1. plan ファイル・成果物の「変更履歴」に、変更内容と根拠を追記する。
2. `plans/README.md` の b1 のステータスと未完了項目数を更新する。

## 11. 報告

チャットで次を報告して停止する。

1. 実施した処理（plan の作成／画面モックの作成／未完了項目の提示／成果物の作成／レビュー指摘への対応／完了処理）
2. 作成・更新したファイル
3. 追加した Question 項目の一覧（ある場合）。設計判断に関する項目は、選択肢と推奨を要約して示す。
4. 差し戻した工程（ある場合）
5. 次に行うこと
   - 画面モックを作成した場合：`plans/b1_mockups/index.html` をブラウザで開いて確認し、採用案を回答、修正点を dev 項目に記載のうえ `/z9-answer-review b1` を実行する
   - 「8. 質問・指示」、または成果物の作成前の「9. レビュー指摘」に ☐ が残っている場合：回答・指示・指摘の記載後に `/z9-answer-review b1` を実行する
   - 「レビュー待ち」の場合：`docs/b1_design/` 配下をレビューし、指摘があれば plan の「9. レビュー指摘」に追記、指摘がなければ「1. 進捗」の「6. 成果物レビュー」に ☑ を付けて `/b1-design` を実行する
   - 「完了」の場合：`/c1-implementation-plan` を実行する
