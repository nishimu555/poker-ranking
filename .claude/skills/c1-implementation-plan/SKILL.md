# 実装計画（c1-implementation-plan）

本スキルは `CLAUDE.md` のルールに従う。

## 役割

Microsoft Engineering Playbook に準拠し、要件と設計から漏れなくタスクと完了条件を導くテックリードとして作業する。

- 担うこと：開発の前提を整理し、設計をタスクに分解し、依存関係・完了条件・テスト期待値の概要を明らかにする。開発の前提に関する選択肢を比較して推奨を示す。
- 決めないこと：開発の前提として採用する方式・ツール、依存関係以外の優先順位、実装の範囲やスケジュール。開発者が決める。

## 入力と成果物

| 項目 | パス |
|---|---|
| 入力 | `docs/b1_design/component-design.md`、`docs/b1_design/decisions/`、`docs/a1_requirements/requirements.md` |
| plan ファイル | `plans/c1_implementation-plan.md`（テンプレート：`templates/plan.md`） |
| 成果物 | `docs/c1_implementation-plan/implementation-plan.md`（テンプレート：`templates/c1_implementation-plan.md`） |

参考にする開発手法：GitHub Spec Kit（タスク分解）、Microsoft Engineering Playbook（完了条件）

## 1. 開始条件の確認

1. `plans/b1_design.md` のステータスが「完了」であることを確認する。満たさない場合は処理を行わず、その旨を報告して停止する。
2. 入力をすべて読み込む。
3. `plans/c1_implementation-plan.md` の状態を確認し、次のいずれかの処理を行う。

| plan ファイルの状態 | 処理 |
|---|---|
| 存在しない | 「3. plan の作成」 |
| 「8. 質問・指示」、またはステータスが「レビュー待ち」以外で「9. レビュー指摘」に ☐ が残っている | 「4. 未完了項目の提示」 |
| 「8. 質問・指示」「9. レビュー指摘」がすべて ☑（成果物未作成、または plan 更新後に未反映） | 「5. 成果物の作成」 |
| 「レビュー待ち」かつ「9. レビュー指摘」に ☐ が残っている | 「6. レビュー指摘への対応」 |
| 「レビュー待ち」かつ「1. 進捗」の「6. 成果物レビュー」が ☑、「9. レビュー指摘」がすべて ☑ | 「7. 完了処理」 |
| 「レビュー待ち」かつ上記以外 | 開発者のレビュー待ちである旨を報告して停止する |

## 2. 作業手順の定義

plan の「5. 作業手順と実行結果」には、次の手順を記載する。本工程は実行を伴わないため「実行結果」は記載しない。

| 手順 | 作業内容 | 参照元 | 作成・更新先 | 実施時期 |
|---|---|---|---|---|
| 5-1. 設計の一覧化 | `Component-XXX`、`Decision-XXXX` と、それぞれに対応する要件を一覧化する | `component-design.md`、`decisions/` | plan「4. 対象範囲」「6. 成果物の構成予定」 | plan の作成 |
| 5-2. 確認観点ごとの記載確認 | 下記の確認観点ごとに根拠資料の記載有無を確認し、記載がない・曖昧・矛盾する観点を Question 項目にする。開発の前提は、選択肢と推奨を付けて Question 項目にする | 入力すべて | plan「8. 質問・指示」 | plan の作成 |
| 5-3. 開発の前提の作成 | ディレクトリ構成、コーディング規約・フォーマッタ、静的解析ツール、脆弱性チェックツールと許容する基準、テストの実行環境とツール、デプロイの方法、ブランチ運用、依存ライブラリの管理方法を記載する | plan の確定した回答・指示、`decisions/` | `implementation-plan.md`（2. 開発の前提） | 成果物の作成 |
| 5-4. タスクの分解 | 下記の分解基準に従い、Component をタスク（`Task-XXX`）に分解する | `component-design.md` | `implementation-plan.md`（3. タスク一覧、4. タスクの詳細） | 成果物の作成 |
| 5-5. テスト期待値の概要の作成 | タスクごとに、条件と期待される結果を由来と共に記載する | `requirements.md`（受け入れ条件）、`component-design.md`（インターフェース）、plan の確定した回答・指示 | `implementation-plan.md`（4. タスクの詳細） | 成果物の作成 |
| 5-6. 依存関係と実装の順序の作成 | タスク間の依存関係を Mermaid で記載し、実装の順序を定める | `implementation-plan.md`（4. タスクの詳細） | `implementation-plan.md`（5. 実装の順序） | 成果物の作成 |
| 5-7. 完了条件の作成 | タスクごとに完了条件を記載する | `implementation-plan.md`（2. 開発の前提、4. タスクの詳細） | `implementation-plan.md`（4. タスクの詳細） | 成果物の作成 |
| 5-8. トレーサビリティの確認 | すべての `Component-XXX` がいずれかのタスクに対応していることを確認する | `component-design.md`、`implementation-plan.md` | `implementation-plan.md`（6. トレーサビリティ） | 成果物の作成 |

確認観点（5-2）：

確認観点は `templates/c1_implementation-plan.md` の節と対応させる。テンプレートに節を追加した場合は、確認観点も追加する。

| # | 確認観点 | 確認内容 | 対応するテンプレートの節 |
|---|---|---|---|
| 1 | 対象範囲 | 実装の対象とする Component、対象外とする Component | 1. 概要 |
| 2 | 開発の前提 | ディレクトリ構成、コーディング規約・フォーマッタ、静的解析ツール、脆弱性チェックツールと許容する基準（不合格とする深刻度）、テストの実行環境とツール（テストツール、代用品（モック）の作り方、ローカルで実行できない範囲）、デプロイの方法、ブランチ運用、依存ライブラリの管理方法 | 2. 開発の前提 |
| 3 | タスクの分解 | Component の責務・インターフェースが、タスクに分解できる程度に明確か | 3. タスク一覧、4. タスクの詳細 |
| 4 | テスト期待値 | 各責務について、正常時・異常時の期待される結果が根拠資料から導けるか | 4. タスクの詳細 |
| 5 | 実装の順序 | 依存関係以外の順序の指定（優先度、段階的な公開等）の有無 | 5. 実装の順序 |

開発の前提（確認観点 2）：

- `Constraint-XXX`、`Decision-XXXX` で指定済みの事項は Question 項目とせず、それに従う。
- 指定のない事項は、選択肢（2 つ以上、良い点・悪い点）と推奨（`CLAUDE.md`「3. 推奨のルール」に従い根拠付き）を記載した Question 項目にする。
- 脆弱性チェック（Microsoft SDL：外部コンポーネントの管理）の許容する基準（どの深刻度以上を不合格とするか）は、AI が決めず、必ず Question 項目で開発者に確認する。
- テストの実行環境とツールは、Small テストがローカルで実行できることを前提とする（`CLAUDE.md`「テストの分担」）。設計書「7. 横断的な関心事（テストのしやすさ）」のローカルで確認できない範囲を踏まえて記載する。
- デプロイの方法は、コードでデプロイできる手段（例：GAS の `clasp` を用いたスクリプト、Terraform・Bicep・AWS CDK 等の IaC）がある場合は、それを推奨として Question 項目にする。デプロイは開発者が行う。
- `.devcontainer/` がある場合は、開発の前提で決まった言語・ツールを Dev Container に追加するタスクを計画に含める（`guide/04_sandbox.md` 参照）。Dev Container を使うかどうかは開発者が決める。
- コードでデプロイする場合は、デプロイ用のスクリプトを作成するタスクを計画に含める。認証情報等の秘密情報を Git の管理対象外とすることを完了条件に含める。

## 3. plan の作成

1. `templates/plan.md` に従って `plans/c1_implementation-plan.md` を作成し、「5. 作業手順と実行結果」に「2. 作業手順の定義」の手順を記載する。
2. 手順 5-1、5-2 を実行し、それぞれ ☑ を付ける。
3. 根拠資料に記載がない、または記載が曖昧・矛盾している観点は、推測で補完せず Question 項目として記載する。質問ごとに「根拠」（どの資料のどこに記載がないか）を記載する。
4. 設計そのものに不足・矛盾がある場合は b1 の plan に、要件そのものに不足・矛盾がある場合は a1 の plan に Question 項目を追記し、「8. 他工程への影響」に従って差し戻す。
5. 「6. 成果物の構成予定」に、作成予定のタスクの一覧（Component 単位の見込み）と由来を記載する。
6. 「1. 進捗」の「1. plan 作成」に ☑ と日時を付け、ステータスを「回答待ち」とする。
7. 成果物は作成しない。

## 4. 未完了項目の提示

1. 「8. 質問・指示」と、成果物の作成前の「9. レビュー指摘」の ☐ の項目を一覧で提示する。
2. 開発者の回答・指示の記載後に `/z9-answer-review c1` を実行するよう案内して停止する。
3. plan・成果物は変更しない。

## 5. 成果物の作成

1. ステータスを「確定」とし、「1. 進捗」の「4. plan 確定」に ☑ と日時を付ける。
2. `templates/c1_implementation-plan.md` に従って `docs/c1_implementation-plan/implementation-plan.md` を作成する。すでに存在する場合は、plan の変更内容に基づいて更新する。
3. 手順 5-3〜5-8 を実行し、それぞれ ☑ を付ける。記載ルールは次のとおり。
   - タスクの分解基準：1 つのタスクは、1 つの Component の 1 つの責務とし、1 回のコミットでレビューできる大きさとする。
   - タスクは `Task-XXX` とし、対象の Component、対応する要件、依存するタスク、作業内容、作成・更新する予定のファイル、完了条件、テスト期待値の概要を記載する。
   - テスト期待値の概要は、条件と期待される結果を記載し、由来（`Feature-XXX` の受け入れ条件、`Component-XXX` のインターフェース、`c1/Question-XXX` 等）を必ず記載する。由来のない期待値は記載しない。正常時・異常時の期待値が根拠資料から導けない場合は Question 項目で確認する。
   - 完了条件は、全タスク共通の条件（ビルドが成功する、「2. 開発の前提」の静的解析ツールで指摘が 0 件、脆弱性チェックで許容する基準を超える脆弱性が 0 件、テスト期待値を確認する Small テストがすべて成功する、`implementation-design.md` が更新されている）に、根拠資料にタスク固有の条件があれば追加する。
   - 実装の順序は依存関係に従う。依存関係のないタスク同士は、開発者の指定があればそれに従い、なければ `Task-XXX` の番号順とする。
   - 依存関係は Mermaid で記載する。
   - すべての記載に由来を記載する。由来のない記載はしない。
4. 作成中に不明点が見つかった場合、または対応先のない Component がある場合は、作成を中断し、plan に Question 項目を追記して、ステータスを「回答待ち」に戻し、「1. 進捗」の「2.」〜「5.」の ☑ を外して停止する。
5. 作成が完了したら、「1. 進捗」の「5. 成果物作成」に ☑ と日時を付け、ステータスを「レビュー待ち」とする。既存の成果物を更新した場合（差し戻し後の再作成等）で「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。

## 6. レビュー指摘への対応

1. 「9. レビュー指摘」の ☐ の review 項目それぞれについて、指摘に基づき `implementation-plan.md` を修正する。
   - ID がない場合は、開発者の記載内容を変更せず ID のみを付与する。
   - 修正箇所を「AI対応内容」に記載し、☑ を付け、「AI確認結果」に確認内容を記載する。
2. 指摘の解釈が一意に定まらない場合、または根拠資料・確定事項と矛盾する場合は ☑ を付けず、「8. 質問・指示」に Question 項目を追記し、ステータスを「回答待ち」として停止する。このとき「1. 進捗」の「2.」〜「5.」の ☑ を外す。
3. 成果物を修正した場合、「1. 進捗」の「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。
4. 修正後もステータスは「レビュー待ち」のままとし、開発者に再レビューを依頼する。

## 7. 完了処理

1. ステータスを「完了」とする。
2. 次工程（`/c2-implement`、`/c3-test-plan`。並行して実施できる）の実行を案内する。

## 8. 他工程への影響

- 設計の不足・矛盾が見つかった場合は b1 の plan ファイルに、要件の不足・矛盾が見つかった場合は a1 の plan ファイルに Question 項目を追記して差し戻す。
- 成果物を更新した場合、後続工程（c2 以降）の plan ファイルが存在していれば、影響先の plan ファイルに Question 項目を追記して差し戻す。テスト期待値を変更した場合は c2・c3 の両方が影響先となる。
- いずれも `CLAUDE.md`「6. 工程ゲート」に従う。影響先の plan の本文・成果物は変更しない。影響先の plan のステータスを「差し戻し」とし、「1. 進捗」の「2.」〜「5.」の ☑ を外す。「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。

## 9. 記録

1. plan ファイル・成果物の「変更履歴」に、変更内容と根拠を追記する。
2. `plans/README.md` の c1 のステータスと未完了項目数を更新する。

## 10. 報告

チャットで次を報告して停止する。

1. 実施した処理（plan の作成／未完了項目の提示／成果物の作成／レビュー指摘への対応／完了処理）
2. 作成・更新したファイル
3. 追加した Question 項目の一覧（ある場合）。開発の前提に関する項目は、選択肢と推奨を要約して示す。
4. 差し戻した工程（ある場合）
5. 次に行うこと
   - 「8. 質問・指示」、または成果物の作成前の「9. レビュー指摘」に ☐ が残っている場合：回答・指示・指摘の記載後に `/z9-answer-review c1` を実行する
   - 「レビュー待ち」の場合：`docs/c1_implementation-plan/implementation-plan.md` をレビューし、指摘があれば plan の「9. レビュー指摘」に追記、指摘がなければ「1. 進捗」の「6. 成果物レビュー」に ☑ を付けて `/c1-implementation-plan` を実行する
   - 「完了」の場合：`/c2-implement` と `/c3-test-plan` を実行する（並行して実施できる）
