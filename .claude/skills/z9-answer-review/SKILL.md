# 回答確認（z9-answer-review）

対象工程：`$ARGUMENTS`

本スキルは `CLAUDE.md` のルールに従う。本スキル自体は plan を作成しない。

## 役割

回答を根拠資料や確定事項と照らし合わせ、矛盾と不足を見逃さないレビュアーとして作業する。

- 担うこと：開発者の回答・指示が根拠資料や確定事項と矛盾しないか、工程を進めるのに十分かを確認し、不足があれば追加の質問として明らかにする。
- 決めないこと：回答内容の良し悪し、採用する方針（開発者が決める）。

## 1. 対象の特定

1. 工程記号が指定されていない、または `CLAUDE.md`「4. 工程一覧」に存在しない場合は、処理を行わず、工程記号の指定を求めて停止する。
2. 対象は `CLAUDE.md`「4. 工程一覧」に記載された、指定工程の plan ファイル 1 つのみとする。
3. plan ファイルが存在しない場合は、処理を行わず、その工程のスキルの実行を案内して停止する。
4. 判断の根拠として、`CLAUDE.md`「2. 基本原則」に記載された資料を読み込む。
5. 確認対象は次のとおりとする。
   - 「8. 質問・指示」の項目
   - ステータスが「レビュー待ち」以外（成果物の作成前）の場合は、「9. レビュー指摘」の review 項目（plan・plan の添付への指摘）も対象とする（「3-2. review 項目への対応（成果物の作成前）」）
   - ステータスが「レビュー待ち」の場合の review 項目は、成果物の修正を伴うため本スキルでは扱わず、各工程のスキルで対応する
   - ai-review 項目（`/r1-final-review` が記載する AI からのレビュー指摘）は、本スキルでは扱わず、「開発者判断」の記入後に各工程のスキル（c2・c4）で対応する

## 2. Question 項目の確認

☐ の Question 項目それぞれについて、次を行う。

| 状態 | 対応 |
|---|---|
| 「開発者回答」が空欄 | 変更しない。未回答として報告対象にする |
| 回答が `CLAUDE.md`「7. ☑ のルール」の条件を満たす | ☑ を付け、「AI確認結果」に確認内容（照合した資料・確定事項）を記載する |
| 条件を満たさない | ☐ のまま残し、「AI確認結果」に不足点・矛盾点を事実として記載し、直下に枝番の Question 項目（例：`Question-001-1`）を追記する |

- 開発者回答の記載内容は変更しない。
- 回答の解釈が一意に定まらない場合は、解釈を推測せず、枝番の Question 項目で確認する。

## 3. dev 項目への対応

☐ の dev 項目それぞれについて、次を行う。

1. ID がない場合は、「開発者からの質問・指示」を変更せず、その plan ファイル内の次の連番で `dev-XXX` を付与する。ID が重複している、または書式が誤っている（全角数字等）場合は、記載内容を変更せず ID のみを正しい連番に付け直し、変更履歴に元の ID と新しい ID を記録する。
2. 内容に応じて対応し、「AI対応内容」に記載する。
   - 質問の場合：根拠資料に基づいて回答する。根拠資料で回答できない場合は、その旨を記載し、Question 項目を追記する。
   - 指示の場合：plan 本文に反映し、反映箇所を記載する。
3. 対応が完了したら ☑ を付け、「AI確認結果」に確認内容を記載する。
4. 次の場合は ☑ を付けず、Question 項目を追記して確認する。
   - 指示が `docs/a0_request/request.md` または他の確定事項と矛盾する場合
   - 指示の解釈が一意に定まらない場合

## 3-2. review 項目への対応（成果物の作成前）

ステータスが「レビュー待ち」以外の場合、「9. レビュー指摘」の ☐ の review 項目それぞれについて、次を行う。

1. ID がない、重複している、または書式が誤っている場合は、「3. dev 項目への対応」の 1. と同じく ID のみを付与・付け直す。
2. 指摘の対象を確認し、次のとおり対応する。
   - plan 本文・plan の添付（画面モック等）への指摘：plan 本文・添付に反映し、「AI対応内容」に反映箇所を記載して ☑ を付け、「AI確認結果」に確認内容を記載する。
   - 他工程の確定事項（要件等）の変更を伴う指摘：「5. 他工程への影響」に従い、影響先の plan に Question 項目を追記して差し戻す。review 項目は ☐ のまま残し、「AI対応内容」に差し戻し先と追記した Question 項目（例：`a1/Question-024`）を記載する。影響先の工程が完了した後、本スキルを再実行して反映し、☑ を付ける。
3. 次の場合は ☑ を付けず、「8. 質問・指示」に Question 項目を追記して確認する。
   - 指摘の解釈が一意に定まらない場合
   - 指摘が `docs/a0_request/request.md` または他の確定事項と矛盾する場合
4. 数の指定のない「案の追加・作り直し」の指摘は、作成前に Question 項目で数を確認する。

## 4. plan 本文への反映

- ☑ にした Question 項目の回答、および対応した dev 項目・review 項目の内容を、plan 本文の該当セクションに反映する。
- 反映した箇所には、由来となる項目 ID（例：`Question-003`、`dev-001`、`review-001`）を併記する。
- plan の添付（`plans/<工程記号>_mockups/` の画面モック等）は plan の一部として扱い、回答・指示に基づいて修正する。修正したファイルの先頭のコメントに、由来となる項目 ID を追記する。
- 数の指定のない「案の追加・作り直し」の指示は、作成前に Question 項目で数を確認する。
- 成果物は変更しない（成果物の更新は各工程のスキルで行う）。

## 5. 他工程への影響

回答・指示により他工程の内容に変更が必要になった場合は、`CLAUDE.md`「6. 工程ゲート」に従う。

1. 影響先の工程の plan ファイルに、その plan の次の連番で Question 項目を追記する。
   - 「根拠」に影響元の項目を `a1/Question-001`、`a1/dev-002` の形式で記載する。
   - 影響範囲（関連する ID）を記載する。
2. 影響先の plan 本文・成果物は直接変更しない。
3. 影響先の工程を差し戻しとして扱う。影響先の plan のステータスを「差し戻し」とし、「1. 進捗」の「2.」〜「5.」の ☑ を外す。「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。

## 6. 記録

1. 「8. 質問・指示」と、成果物の作成前の「9. レビュー指摘」がすべて ☑ になった場合は、「1. 進捗」の「2. 質問への回答・指示の記入」「3. 回答の確認」に ☑ と日時を付ける。
2. 対象 plan ファイル（および Question を追記した他工程の plan ファイル）の「変更履歴」に、変更内容と根拠を追記する。
3. `plans/README.md` の該当工程のステータスと未完了項目数を更新する。差し戻した工程は「差し戻し」とする。

## 7. 報告

チャットで次を報告して停止する。成果物の作成は行わない。

1. ☑ にした項目の一覧（review 項目を含む）
2. 追加した Question 項目の一覧
3. 未回答・未対応の項目の一覧
4. 差し戻した工程と追記した Question 項目の一覧（ある場合）
5. 次に行うこと
   - 「8. 質問・指示」、または成果物の作成前の「9. レビュー指摘」に ☐ が残っている場合：開発者の回答後に `/z9-answer-review <工程記号>` を再実行する（差し戻し中の場合は、差し戻し先の工程を先に完了させる）
   - 「8. 質問・指示」「9. レビュー指摘」がすべて ☑ の場合：plan 本文を確認のうえ、その工程のスキル（例：`/a1-requirements`）を実行すると成果物を作成する
