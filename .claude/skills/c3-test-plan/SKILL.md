# テスト計画（c3-test-plan）

本スキルは `CLAUDE.md` のルールに従う。

## 役割

Google のテストサイズ分類に準拠し、すべての要件をテストケースに対応させるテストエンジニアとして作業する。

- 担うこと：要件・設計・実装計画からテストケースを導き、サイズ・実行環境・実行者を定め、開発者が実行するテストの手順を用意する。すべての要件がいずれかのテストケースで確認されることを保証する。
- 決めないこと：合格の基準、テストの実行環境の選択、Small テストの期待値（c1 で定める）。開発者が決める。

## 入力と成果物

| 項目 | パス |
|---|---|
| 入力 | `docs/a1_requirements/requirements.md`、`docs/b1_design/component-design.md`、`docs/c1_implementation-plan/implementation-plan.md` |
| plan ファイル | `plans/c3_test-plan.md`（テンプレート：`templates/plan.md`） |
| 成果物 | `docs/c3_test-plan/test-plan.md`（テンプレート：`templates/c3_test-plan.md`） |

参考にする開発手法：Google テストサイズ分類（Small / Medium / Large）、Microsoft SDL（セキュリティテスト）、Microsoft Engineering Playbook（デプロイの自動化）

## 1. 開始条件の確認

1. `plans/c1_implementation-plan.md` のステータスが「完了」であることを確認する。満たさない場合は処理を行わず、その旨を報告して停止する。本工程は c2 と並行して実施できる。
2. 入力をすべて読み込む。
3. `plans/c3_test-plan.md` の状態を確認し、次のいずれかの処理を行う。

| plan ファイルの状態 | 処理 |
|---|---|
| 存在しない | 「3. plan の作成」 |
| 「8. 質問・指示」、またはステータスが「レビュー待ち」以外で「9. レビュー指摘」に ☐ が残っている | 「4. 未完了項目の提示」 |
| 「8. 質問・指示」「9. レビュー指摘」がすべて ☑（成果物未作成、または plan 更新後に未反映） | 「5. 成果物の作成」 |
| 「レビュー待ち」かつ「9. レビュー指摘」に ☐ が残っている | 「6. レビュー指摘への対応」 |
| 「レビュー待ち」かつ「1. 進捗」の「6. 成果物レビュー」が ☑、「9. レビュー指摘」がすべて ☑ | 「7. 完了処理」 |
| 「レビュー待ち」かつ上記以外 | 開発者のレビュー待ちである旨を報告して停止する |

## 2. 作業手順の定義

plan の「5. 作業手順と実行結果」には、次の手順を記載する。本工程は実行を伴わないため「実行結果」は記載しない。

| 手順 | 作業内容 | 参照元 | 作成・更新先 | 実施時期 |
|---|---|---|---|---|
| 5-1. テスト対象の一覧化 | `Feature-XXX`、`Quality-XXX`、脅威分析の対策、c1 のテスト期待値を一覧化する | 入力すべて | plan「4. 対象範囲」「6. 成果物の構成予定」 | plan の作成 |
| 5-2. 確認観点ごとの記載確認 | 下記の確認観点ごとに根拠資料の記載有無を確認し、記載がない・曖昧・矛盾する観点を Question 項目にする | 入力すべて | plan「8. 質問・指示」 | plan の作成 |
| 5-3. テストの方針の作成 | サイズごとの実行環境・実行者・テストツールを記載する | `implementation-plan.md`（2. 開発の前提）、`component-design.md`（7. テストのしやすさ）、plan の確定した回答・指示 | `test-plan.md`（2. テストの方針） | 成果物の作成 |
| 5-4. Small テストケースの登録 | c1 のテスト期待値を内容を変えずに Small テストケースとして登録し、`Test-XXX` を付与する | `implementation-plan.md`（4. タスクの詳細） | `test-plan.md`（3. テストケース一覧、4. Small テストケース） | 成果物の作成 |
| 5-5. Medium・Large テストケースの作成 | 受け入れ条件、非機能要件の確認基準、脅威分析の対策、ローカルで確認できない範囲から、Medium・Large のテストケースを作成する | `requirements.md`、`component-design.md`、plan の確定した回答・指示 | `test-plan.md`（3. テストケース一覧、5. Medium・Large テストケース） | 成果物の作成 |
| 5-6. 開発者が実行するテストの手順の作成 | 実行者が開発者のテストについて、事前準備・デプロイ手順・実施手順・結果の記載方法を記載する | `implementation-plan.md`（2. 開発の前提：デプロイの方法） | `test-plan.md`（6. 開発者が実行するテストの手順） | 成果物の作成 |
| 5-7. 合格の基準の作成 | 開発者が定めた合格の基準を記載する | plan の確定した回答・指示 | `test-plan.md`（7. 合格の基準） | 成果物の作成 |
| 5-8. トレーサビリティの確認 | すべての `Feature-XXX`・`Quality-XXX`・c1 のテスト期待値が、いずれかのテストケースに対応していることを確認する | `requirements.md`、`implementation-plan.md`、`test-plan.md` | `test-plan.md`（8. トレーサビリティ） | 成果物の作成 |

確認観点（5-2）：

確認観点は `templates/c3_test-plan.md` の節と対応させる。テンプレートに節を追加した場合は、確認観点も追加する。

| # | 確認観点 | 確認内容 | 対応するテンプレートの節 |
|---|---|---|---|
| 1 | 対象範囲 | テストの対象とする要件、対象外とする要件 | 1. 概要 |
| 2 | テストの方針 | サイズごとの実行環境（ローカル／デプロイ先／実機・外部サービス）と実行者（AI／開発者）、テストツール | 2. テストの方針 |
| 3 | Medium・Large の対象 | 受け入れ条件・非機能要件の確認基準が、テストで確認できる形（数値・条件）で記載されているか。ローカルで確認できない範囲 | 5. Medium・Large テストケース |
| 4 | 開発者が実行するテスト | 手順に必要な情報（デプロイ先、テスト用のアカウント、テストデータ、実機の種類等） | 6. 開発者が実行するテストの手順 |
| 5 | 合格の基準 | 合格とする条件（全件成功が必要か、許容する失敗の有無等） | 7. 合格の基準 |

- 合格の基準は AI が決めず、必ず Question 項目で開発者に確認する。
- テストの実行環境・実行者が `implementation-plan.md`「2. 開発の前提」で定まっていない場合は、選択肢と推奨を付けた Question 項目にする。

## 3. plan の作成

1. `templates/plan.md` に従って `plans/c3_test-plan.md` を作成し、「5. 作業手順と実行結果」に「2. 作業手順の定義」の手順を記載する。
2. 手順 5-1、5-2 を実行し、それぞれ ☑ を付ける。
3. 根拠資料に記載がない、または記載が曖昧・矛盾している観点は、推測で補完せず Question 項目として記載する。質問ごとに「根拠」（どの資料のどこに記載がないか）を記載する。
4. c1 のテスト期待値そのものに不足・矛盾がある場合は c1、設計の不足・矛盾は b1、要件の不足・矛盾（確認基準が数値・条件になっていない等）は a1 の plan に Question 項目を追記し、「8. 他工程への影響」に従って差し戻す。
5. 「6. 成果物の構成予定」に、作成予定のテストケースの件数（サイズ別）と由来を記載する。
6. 「1. 進捗」の「1. plan 作成」に ☑ と日時を付け、ステータスを「回答待ち」とする。
7. 成果物は作成しない。

## 4. 未完了項目の提示

1. 「8. 質問・指示」と、成果物の作成前の「9. レビュー指摘」の ☐ の項目を一覧で提示する。
2. 開発者の回答・指示の記載後に `/z9-answer-review c3` を実行するよう案内して停止する。
3. plan・成果物は変更しない。

## 5. 成果物の作成

1. ステータスを「確定」とし、「1. 進捗」の「4. plan 確定」に ☑ と日時を付ける。
2. `templates/c3_test-plan.md` に従って `docs/c3_test-plan/test-plan.md` を作成する。すでに存在する場合は、plan の変更内容に基づいて更新する。
3. 手順 5-3〜5-8 を実行し、それぞれ ☑ を付ける。記載ルールは次のとおり。
   - テストケースは `Test-XXX` とし、サイズ、対象（`Component-XXX`、`Task-XXX`）、条件・手順、期待される結果、実行環境、実行者、由来を記載する。
   - Small テストケースは、c1 のテスト期待値の内容を変えずに登録し、由来に `Task-XXX 期待値N` を記載する。
   - Medium・Large テストケースは、`Feature-XXX` の受け入れ条件、`Quality-XXX` の確認基準、設計書の脅威分析の対策（セキュリティテスト：Microsoft SDL）、設計書「7. テストのしやすさ」のローカルで確認できない範囲から導く。由来のないテストケースは記載しない。
   - 実行者が開発者のテストケースは、「6. 開発者が実行するテストの手順」に、事前準備、デプロイ手順（実行するコマンド、コードでデプロイできない場合は操作手順）、実施手順、期待される結果、結果の記載方法を記載する。認証情報等の秘密情報は手順に記載せず、扱い方のみを記載する。
   - 合格の基準は、開発者の回答をそのまま記載する。
4. 作成中に不明点が見つかった場合、または対応するテストケースのない要件・期待値がある場合は、作成を中断し、plan に Question 項目を追記して、ステータスを「回答待ち」に戻し、「1. 進捗」の「2.」〜「5.」の ☑ を外して停止する。
5. 作成が完了したら、「1. 進捗」の「5. 成果物作成」に ☑ と日時を付け、ステータスを「レビュー待ち」とする。既存の成果物を更新した場合（差し戻し後の再作成等）で「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。

## 6. レビュー指摘への対応

1. 「9. レビュー指摘」の ☐ の review 項目それぞれについて、指摘に基づき `test-plan.md` を修正する。
   - ID がない場合は、開発者の記載内容を変更せず ID のみを付与する。
   - 修正箇所を「AI対応内容」に記載し、☑ を付け、「AI確認結果」に確認内容を記載する。
2. 指摘が Small テストケースの期待値の変更を伴う場合は、c1 の plan に Question 項目を追記して差し戻す。
3. 指摘の解釈が一意に定まらない場合、または根拠資料・確定事項と矛盾する場合は ☑ を付けず、「8. 質問・指示」に Question 項目を追記し、ステータスを「回答待ち」として停止する。このとき「1. 進捗」の「2.」〜「5.」の ☑ を外す。
4. 成果物を修正した場合、「1. 進捗」の「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。
5. 修正後もステータスは「レビュー待ち」のままとし、開発者に再レビューを依頼する。

## 7. 完了処理

1. ステータスを「完了」とする。
2. 次工程（`/c4-test`）の実行を案内する。c4 は c2 の完了も必要である旨を併せて案内する。

## 8. 他工程への影響

- テスト期待値の不足・誤りは c1、設計の不足・矛盾は b1、要件の不足・矛盾は a1 の plan ファイルに Question 項目を追記して差し戻す。
- 成果物を更新した場合、後続工程（c4 以降）の plan ファイルが存在していれば、影響先の plan ファイルに Question 項目を追記して差し戻す。
- いずれも `CLAUDE.md`「6. 工程ゲート」に従う。影響先の plan の本文・成果物は変更しない。影響先の plan のステータスを「差し戻し」とし、「1. 進捗」の「2.」〜「5.」の ☑ を外す。「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。

## 9. 記録

1. plan ファイル・成果物の「変更履歴」に、変更内容と根拠を追記する。
2. `plans/README.md` の c3 のステータスと未完了項目数を更新する。

## 10. 報告

チャットで次を報告して停止する。

1. 実施した処理（plan の作成／未完了項目の提示／成果物の作成／レビュー指摘への対応／完了処理）
2. 作成・更新したファイル
3. テストケースの件数（サイズ別、実行者別）
4. 追加した Question 項目の一覧（ある場合）
5. 差し戻した工程（ある場合）
6. 次に行うこと
   - 「8. 質問・指示」、または成果物の作成前の「9. レビュー指摘」に ☐ が残っている場合：回答・指示・指摘の記載後に `/z9-answer-review c3` を実行する
   - 「レビュー待ち」の場合：`docs/c3_test-plan/test-plan.md` をレビューし、指摘があれば plan の「9. レビュー指摘」に追記、指摘がなければ「1. 進捗」の「6. 成果物レビュー」に ☑ を付けて `/c3-test-plan` を実行する
   - 「完了」の場合：c2 の完了後に `/c4-test` を実行する
