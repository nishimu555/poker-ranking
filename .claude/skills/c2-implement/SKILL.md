# 実装（c2-implement）

実行モード：`$ARGUMENTS`（空欄：1 タスクを実装して停止／「連続」：停止する理由がない限り残りのタスクを続けて実装）

本スキルは `CLAUDE.md` のルールに従う。

## 役割

実装計画と設計に忠実で、Microsoft SDL のセキュアコーディングに準拠するソフトウェアエンジニアとして作業する。

- 担うこと：実装計画のテスト期待値から Small テストを先に作成し、テストを満たすように実装する。静的解析・脆弱性チェックの基準を満たし、実装設計書を最新に保つ。
- 決めないこと：計画にない仕様、計画にないライブラリの追加、テスト期待値の変更。開発者が決める。

## 入力と成果物

| 項目 | パス |
|---|---|
| 入力 | `docs/c1_implementation-plan/implementation-plan.md`、`docs/b1_design/component-design.md`、`docs/b1_design/decisions/`、`docs/a1_requirements/requirements.md` |
| plan ファイル | `plans/c2_implement.md`（テンプレート：`templates/plan.md`） |
| 成果物 | `src/`、`tests/`（Small テスト） |
| 成果物 | `docs/c2_implement/implementation-design.md`（テンプレート：`templates/c2_implementation-design.md`） |

参考にする開発手法：Microsoft Engineering Playbook（コミット規約・コードレビュー）、Microsoft SDL（静的解析・依存ライブラリの確認）

## 1. 開始条件の確認

1. `plans/c1_implementation-plan.md` のステータスが「完了」であることを確認する。満たさない場合は処理を行わず、その旨を報告して停止する。
2. 入力をすべて読み込む。実装済みのコードは `docs/c2_implement/implementation-design.md` を読み、必要なファイルのみを読む。
3. `plans/c2_implement.md` の状態を確認し、次のいずれかの処理を行う。

| plan ファイルの状態 | 処理 |
|---|---|
| 存在しない | 「3. plan の作成」 |
| 「9. レビュー指摘」に ☐ の ai-review 項目がある（ステータスを問わない。最終レビュー・中間チェック（`/r1-final-review`）で記録されたもの） | 「6. レビュー指摘への対応」の「AI からのレビュー指摘（ai-review）への対応」 |
| 「8. 質問・指示」、またはステータスが「レビュー待ち」以外で「9. レビュー指摘」に ☐ の review 項目が残っている | 「4. 未完了項目の提示」 |
| 「8. 質問・指示」「9. レビュー指摘」がすべて ☑、かつ未実装のタスクがある | 「5. 実装」 |
| 「レビュー待ち」かつ「9. レビュー指摘」に ☐ が残っている | 「6. レビュー指摘への対応」 |
| 「レビュー待ち」かつ「1. 進捗」の「6. 成果物レビュー」が ☑、「9. レビュー指摘」がすべて ☑ | 「7. 完了処理」 |
| 「レビュー待ち」かつ上記以外 | 開発者のレビュー待ちである旨を報告して停止する |

## 2. 作業手順の定義

plan の「5. 作業手順と実行結果」には、次の手順を記載する。本工程は実行を伴うため、各手順に「実行結果」を記載する。

| 手順 | 作業内容 | 参照元 | 作成・更新先 |
|---|---|---|---|
| 5-1. 開発環境の準備 | 実装計画「2. 開発の前提」に従い、ディレクトリ構成、フォーマッタ、静的解析ツール、脆弱性チェックツール、テストツールを設定する | `implementation-plan.md`（2. 開発の前提） | 設定ファイル、`implementation-design.md` |
| 5-2 以降. Task-XXX：<名称> | 実装計画の実装の順序に従い、1 タスクにつき 1 手順とする。内容は「5. 実装」の「1 タスクの流れ」に従う | `implementation-plan.md`（4. タスクの詳細） | `src/`、`tests/`、`implementation-design.md` |
| 最後. 実装設計書の全体確認 | `implementation-design.md` がコード全体と一致していること、「5. 計画との違い」が記載されていることを確認する | `src/`、`tests/`、`implementation-plan.md` | `implementation-design.md` |

各タスクの手順の「実行結果」には、次を記載する。

- テスト作成後の失敗の確認（失敗した件数と理由）
- 実装後のテスト結果（成功件数／全件数）、ビルド結果
- 静的解析の指摘件数、脆弱性チェックの結果（許容する基準を超える件数）
- 計画との差異とその根拠（ある場合）
- コミット（AI がタスクの変更をコミットした後、「コミット：<ID> <メッセージ>」の形式で記入する。push は開発者が行う。「5. 実装」の「git の扱い」参照）

## 3. plan の作成

1. `templates/plan.md` に従って `plans/c2_implement.md` を作成し、「5. 作業手順と実行結果」に「2. 作業手順の定義」の手順を、実装計画のタスク数に応じて記載する。
2. 次の確認観点ごとに根拠資料の記載有無を確認し、記載がない・曖昧・矛盾する観点は Question 項目として記載する。

| # | 確認観点 | 確認内容 |
|---|---|---|
| 1 | タスクの明確さ | 各タスクの作業内容・作成予定のファイル・テスト期待値が、実装に着手できる程度に明確か |
| 2 | 開発環境 | 開発の前提のツール・実行環境が、この環境で利用できるか（バージョン確認コマンド等で確認し、結果を事実として記載する） |

3. 実装計画そのものに不足・矛盾がある場合は c1 の plan に Question 項目を追記し、「8. 他工程への影響」に従って差し戻す。
4. 「6. 成果物の構成予定」に、タスクの一覧と作成予定のファイルを記載する。
5. 「1. 進捗」の「1. plan 作成」に ☑ と日時を付ける。Question 項目がある場合はステータスを「回答待ち」とする。Question 項目がない場合は「8. 質問・指示」「9. レビュー指摘」がすべて ☑ の状態として扱う。
6. 実装は行わない。

## 4. 未完了項目の提示

1. 「8. 質問・指示」と、成果物の作成前の「9. レビュー指摘」の ☐ の項目を一覧で提示する。
2. 開発者の回答・指示の記載後に `/z9-answer-review c2` を実行するよう案内して停止する。
3. plan・成果物は変更しない。

## 5. 実装

### 実行前の確認

1. ステータスが「確定」でない場合は「確定」とし、「1. 進捗」の「4. plan 確定」に ☑ と日時を付ける。
2. `git status` で未コミットの変更を確認する。
   - `plans/`・`docs/c2_implement/` 以外（`src/`、`tests/`、設定ファイル等）に未コミットの変更がある場合は、その一覧を報告し、次のタスクのコミットに含めるか、開発者がコミット・破棄するかを開発者に確認して停止する。開発者が含めてよいと回答した場合は続行する。
   - `plans/`・`docs/c2_implement/` の変更（前回の「コミット」欄の記入、開発者の回答の記入等）は、次のタスクのコミットに含める。
3. 前回実装したタスクの「コミット」欄が空欄の場合は、その旨を報告し、AI がコミットして記入するか、記入せずに先に進めてよいかを開発者に確認して停止する。開発者が進めてよいと回答した場合は続行する。
4. 5-1 が未実施の場合は、5-1 を実施してから最初のタスクに進む。

### git の扱い

| 操作 | 実行者 | 内容 |
|---|---|---|
| `git status`・`git diff`・`git log`（確認） | AI | コミットの対象と結果の確認に使う |
| `git add`・`git commit` | AI | タスクの完了時と、レビュー指摘への対応の完了時に行う（「1 タスクの流れ」7、「6. レビュー指摘への対応」） |
| `git push`、ブランチの作成・切り替え、プルリクエスト | 開発者 | AI は実行しない。実施する時期は開発者が判断するため、AI は報告等で push を促さない |
| 履歴の書き換え（`reset`・`rebase`・`commit --amend` 等）、変更の破棄（`checkout -- <file>`・`restore`・`clean` 等） | 開発者 | AI は実行しない |

- `git add` は、そのタスク（または指摘への対応）で作成・変更したファイルと、`plans/`・`docs/c2_implement/` の変更をファイル名を指定して行う。`git add -A`・`git add .` は使わない。
- コミットメッセージは `[Task-XXX] 日本語の概要` の形式とする（CLAUDE.md 10.）。レビュー指摘への対応は `[Task-XXX] review-NNN：日本語の概要` とする。
- コミットのフック等でコミットが失敗した場合は、`--no-verify` 等で回避せず、状況を実行結果に記録して停止する。
- 「コミット」欄にはコミット後に ID とメッセージを記入する。この記入による plan の変更は、次のタスクのコミットに含まれる。

### 1 タスクの流れ

実装計画の実装の順序に従い、未実装の次のタスクについて次を行う。

1. テストの作成：実装計画のテスト期待値の概要だけをもとに Small テストを作成する。テストコードには `// Task-XXX 期待値N` を記載する。
   - Small テストはローカルで実行できるようにし、実行環境固有の機能は実装計画「2. 開発の前提」の方法で代用品（モック）に置き換える。
   - ローカルで確認できない期待値がある場合は、c1 の plan に Question 項目を追記して差し戻す（Medium テストで確認するか等を確認する）。
2. 失敗の確認：テストを実行し、失敗することを確認する。失敗した件数と理由を記録する。
   - 実装前に成功したテストがある場合は、その理由を事実として記録する。テストが期待値を確認できていない場合はテストを修正する。理由が判断できない場合は Question 項目で確認する。
3. 実装：テストが成功するように実装する。次を守る。
   - コードコメントに `// Task-XXX: <説明>` を記載する（日本語）。
   - 設計書「7. 横断的な関心事」の対策（脅威分析の対策、認証・認可、ログ、エラー処理）に従う。
   - 秘密情報（パスワード、API キー等）をコードに記載しない。
   - 実装のコードを見てテストや期待値を変更しない。
4. 完了条件の確認：実装計画のタスクの完了条件（ビルド成功、静的解析の指摘 0 件、許容する基準を超える脆弱性 0 件、Small テスト全成功、タスク固有の条件）をすべて満たすことを確認する。満たさない場合は修正する。
5. 実装設計書の更新：`docs/c2_implement/implementation-design.md` を `templates/c2_implementation-design.md` に従って作成・更新する。更新するまでタスクを完了としない。
6. 記録：手順に ☑ を付け、「実行結果」を記載する。「9. 記録」（変更履歴、`plans/README.md`）もこの時点で行う。
7. コミット：「git の扱い」に従って `git add`・`git commit` を行い、`git log -1` でコミットの ID を確認して、「実行結果」の「コミット」欄に「コミット：<ID> <メッセージ>」を記入する。push はしない。

### 停止する条件

実行モードに関わらず、次の場合は作業を中断して停止する。

- 期待値に誤りがある、期待値のとおりに実装できない、計画にないライブラリが必要になった場合：c1 の plan に Question 項目を追記して差し戻す（「8. 他工程への影響」）。
- 設計・要件の不足・矛盾が見つかった場合：b1 または a1 の plan に Question 項目を追記して差し戻す。
- 本工程の範囲で判断できない不明点がある場合：本 plan に Question 項目を追記し、ステータスを「回答待ち」に戻し、「1. 進捗」の「2.」〜「5.」の ☑ を外す。
- 完了条件を満たせないまま解消できない場合：状況を事実として実行結果に記録し、Question 項目で確認する。

### 実行モードによる違い

| 実行モード | 動作 |
|---|---|
| 空欄 | 1 タスクを実装して停止し、「10. 報告」を行う |
| 連続 | 停止する条件に該当しない限り、次のタスクに進む。タスクごとにコミットする。実行中のタスク間では「実行前の確認」2・3 を行わない（実行の開始時のみ行う）。停止時に、タスクごとの変更ファイルとコミット（ID とメッセージ）を一覧で報告する |

### 全タスクの完了

すべてのタスクが ☑ になったら、最後の手順（実装設計書の全体確認）を実施し、「1. 進捗」の「5. 成果物作成」に ☑ と日時を付け、ステータスを「レビュー待ち」とする。既存の成果物を更新した場合（差し戻し後の再実装等）で「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。

## 6. レビュー指摘への対応

1. 「9. レビュー指摘」の ☐ の review 項目それぞれについて、指摘に基づきコードを修正する（ai-review 項目は下記「AI からのレビュー指摘（ai-review）への対応」）。
   - ID がない場合は、開発者の記載内容を変更せず ID のみを付与する。
   - 修正後、該当タスクの完了条件をすべて満たすことを確認し、`implementation-design.md` を更新する。
   - 修正箇所を「AI対応内容」に記載し、☑ を付け、「AI確認結果」に確認内容を記載する。
   - 「5. 実装」の「git の扱い」に従ってコミットし、「AI対応内容」に「コミット：<ID> <メッセージ>」を記入する。
2. 指摘への対応がテスト期待値の変更を伴う場合は、c1 の plan に Question 項目を追記して差し戻す。
3. 指摘の解釈が一意に定まらない場合、または根拠資料・確定事項と矛盾する場合は ☑ を付けず、「8. 質問・指示」に Question 項目を追記し、ステータスを「回答待ち」として停止する。このとき「1. 進捗」の「2.」〜「5.」の ☑ を外す。
4. 成果物を修正した場合、「1. 進捗」の「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。
5. 修正後もステータスは「レビュー待ち」のままとし、開発者に再レビューを依頼する。

### AI からのレビュー指摘（ai-review）への対応

実装の最終レビュー（`/r1-final-review c2`）・中間チェック（`/r1-final-review 中間`）で記載された ☐ の ai-review 項目は、「開発者判断」に従って次のとおり扱う。review 項目と同時に残っている場合は、review 項目と同じ実行で対応する。

| 開発者判断 | 対応 |
|---|---|
| 空欄 | 対応しない。空欄の項目を一覧で提示し、判断の記入を依頼して停止する（判断が記入済みの他の項目は対応してよい） |
| 対応する | 「推奨」（開発者が直し方を指示した場合はその指示）に従ってコードを修正する。修正後の扱いは review 項目と同じ（上記 1.〜5.。完了条件の確認、`implementation-design.md` の更新、コミット） |
| 対応しない | コードは修正しない。「AI対応内容」に「対応しない（開発者判断：<理由>）」と記載して ☑ を付け、「AI確認結果」に確認内容を記載する |
| その他（指示） | 指示に従って対応する。指示の解釈が一意に定まらない場合は、上記 3. と同じく Question 項目で確認する |

- 「開発者判断」は変更しない（`CLAUDE.md`「8. ファイルの権限」）。
- ai-review への対応は、ステータスに関わらず行う（中間チェックは工程の途中でも記録されるため）。対応後のステータスは次のとおりとする。
  - 「差し戻し」（完了した工程に中間チェックで記録された場合）：すべての ai-review 項目が ☑ になったら「レビュー待ち」とし、開発者に再レビューを依頼する。`plans/README.md` の差し戻し中の工程の記録を解消する
  - 上記以外：ステータスは変更しない。成果物を修正した場合の「6. 成果物レビュー」の扱いは、上記 4. と同じとする
- 対応を終えたら、元の処理（実装・テストの実施等）の続きがある場合は、報告で次に行うことを案内する。
- 「対応する」で修正した場合のコミットメッセージは `[Task-XXX] ai-review-NNN：日本語の概要` とする（Task-XXX は修正したコードのタスク）。
- 修正によりテスト期待値の変更が必要な場合は、上記 2. と同じく c1 に差し戻す。

## 7. 完了処理

1. ステータスを「完了」とする。
2. 次工程（`/c4-test`）の実行を案内する。c4 は c3 の完了も必要である旨を併せて案内する。

## 8. 他工程への影響

- 実装計画（期待値、ライブラリ等）の不足・誤りは c1、設計の不足・矛盾は b1、要件の不足・矛盾は a1 の plan ファイルに Question 項目を追記して差し戻す。
- 成果物を更新した場合、後続工程（c4 以降）の plan ファイルが存在していれば、影響先の plan ファイルに Question 項目を追記して差し戻す。
- いずれも `CLAUDE.md`「6. 工程ゲート」に従う。影響先の plan の本文・成果物は変更しない。影響先の plan のステータスを「差し戻し」とし、「1. 進捗」の「2.」〜「5.」の ☑ を外す。「6. 成果物レビュー」が ☑ であれば外し、変更履歴に理由を記載する。

## 9. 記録

1. plan ファイル・`implementation-design.md` の「変更履歴」に、変更内容と根拠を追記する。
2. `plans/README.md` の c2 のステータスと未完了項目数を更新する。

## 10. 報告

チャットで次を報告して停止する。

1. 実施した処理（plan の作成／未完了項目の提示／実装／レビュー指摘への対応／完了処理）
2. 実装したタスクごとに：
   - 実行結果（失敗の確認、テスト結果、静的解析、脆弱性チェック）
   - 変更したファイル
   - コミット（ID とメッセージ）
3. 追加した Question 項目の一覧（ある場合）
4. 差し戻した工程（ある場合）
5. 次に行うこと
   - 未実装のタスクがある場合：`/c2-implement`（1 タスク）または `/c2-implement 連続` を実行する。次のタスクの名称と内容の要約を併記する。「コミット」欄の記入による plan の変更は未コミットのまま残り、次のタスクのコミットに含まれる旨を併記する
   - 「8. 質問・指示」、または成果物の作成前の「9. レビュー指摘」に ☐ が残っている場合：回答・指示・指摘の記載後に `/z9-answer-review c2` を実行する
   - 「レビュー待ち」の場合：
     - 実装の最終レビューを行っていない場合、または最終レビューの後にコードを修正した場合：`/r1-final-review c2` を実行する（推奨）
